# multi-ai-workflow v2.0 — 星型中枢架构迭代方案

> 基于v1.0实际使用的反馈：真实架构是CC#1中枢 + CC#2副手 + 外部模型群，
> 而非三个角色各司其职的线性流水线。本方案完整重构角色模型。

---

## 一、核心变更：从三角色线性 → 星型中枢

### v1.0 架构问题
```
审查者 ──→ 执行者 ──→ 建模者    （线性，各干各的）
```
这个描述掩盖了真实的复杂度：CC#1不是"审查者"，是所有外部信息的汇合点和决策者。

### v2.0 正确架构
```
              ┌─────────────────────┐
              │    CC#1（中枢大脑）   │
              │  推进·审核·决策·拍板  │
              └──────┬──────┬───────┘
                     │      │
        ┌────────────┘      └────────────┐
        ▼                                ▼
  ┌─────────────┐              ┌──────────────────┐
  │ CC#2（副手） │              │  外部模型群（工具） │
  │ 执行·同步   │              │ 算法·审查·审阅·提取│
  │ 保护CC#1上下文│             │ 多模型交叉对话     │
  └─────────────┘              └──────────────────┘
```

## 二、三角色的重新定义

### CC#1 — 中枢大脑

| 维度 | 描述 |
|------|------|
| **定位** | 项目总指挥，不是简单的"审查者" |
| **核心职责** | 推进项目节奏、审核阶段产出、综合各方意见、做出最终决策 |
| **与外部模型的关系** | **主动驱动**对话——提出问题、追问细节、比较不同模型的意见、最终合成结论。不是被动接收外部输出 |
| **与CC#2的关系** | 分发任务、接收结果、持续同步对齐、通过CC#2保护自己的上下文 |
| **禁止** | 不被大量代码/数据/调试信息淹没上下文 |
| **模型要求** | 强推理+长上下文（如DeepSeek-v4/Claude Opus），能同时追踪多条线索 |

### CC#2 — 核心副手

| 维度 | 描述 |
|------|------|
| **定位** | CC#1的执行代理，**存在意义是保护CC#1的上下文** |
| **核心职责** | 承接CC#1分发的所有需要大量上下文的任务：代码编写、脚本运行、测试执行、数据生成、图表绘制 |
| **与CC#1的关系** | - 项目启动时深度同步（理解完整项目框架）<br>- 项目推进中持续加固对接（阶段间双向确认）<br>- 将执行结果**精简后**汇报给CC#1，不倾倒原始输出 |
| **独立性** | 在自己的会话中独立运行，有自己的上下文窗口，不受CC#1上下文污染 |
| **禁止** | 自行裁决模型局限性、跳过同步加固、向CC#1倾倒大量未处理的原始输出 |
| **模型要求** | 强代码能力+工具调用（同CC#1的底层模型即可，关键是**独立会话**） |

### 外部模型群 — 多功能工具

不是"一个建模者"，是**按需调用的工具集合**：

| 外部模型 | 调用场景 | 模型建议 |
|---------|---------|---------|
| **需求提炼者** | 项目启动时，将用户模糊需求整理为结构化需求文档，交给CC#1审核 | Gemini 3.1 Flash / CC#1自带模型 |
| **算法生成者** | 高难度算法/程序的编写（CC#2不擅长的复杂逻辑） | GPT 5.5 / Gemini 3.1 Pro |
| **代码审查者** | 对CC#2写好的代码做独立算法审查，发现逻辑漏洞 | Gemini 3.1 Pro / Claude Opus |
| **论文审阅者** | 对CC#1生成的论文/文档做独立审阅，发现逻辑漏洞、格式问题 | Gemini 3.1 Pro |
| **文件提取者** | 提取PDF/图片/特殊格式中Claude Code无法直接读取的数据 | Gemini 3.1 Flash / 专用工具 |
| **交叉对话者** | 与CC#1进行多轮对话讨论，从不同角度分析同一结果 | 与CC#1模型不同的任意强模型 |

**关键规则**：
- CC#1 **主动驱动**与外部模型的对话，不是被动接收输出
- 多个外部模型**独立审视**同一份结果，意见不一致时CC#1裁决
- 外部模型之间不直接通信，全部通过CC#1汇聚

## 三、信息流重新设计

### 3.1 CC#1 ↔ CC#2 的同步流

```
项目启动
  ├ CC#1 制定阶段计划 → 交付给CC#2（含完整项目框架）
  ├ CC#2 确认理解 → 开始执行
  │
项目推进中
  ├ CC#2 产生阶段性产出 → 精简汇报给CC#1
  ├ CC#1 审查 → 通过/需修改
  └ 每个阶段结束时双向加固确认
```

**CC#2汇报规范**：
- 不倾倒原始输出（如完整54M行日志）
- 汇报格式：做了什么 → 结果摘要 → 遇到的问题 → 需要CC#1决策的事项
- 原始输出保留在CC#2会话中，CC#1需要时才调取

### 3.2 CC#1 ↔ 外部模型 的对话流

```
CC#1 持有完整项目上下文
  │
  ├ 向模型A发起对话（只给相关片段，不给全部上下文）
  │   ├ CC#1: "这是我们的算法伪代码，请分析复杂度"
  │   ├ 模型A: 分析结果
  │   ├ CC#1: "第3步的剪枝条件在N=10时会不会误剪？"
  │   └ 模型A: 进一步分析 → CC#1综合
  │
  ├ 向模型B发起对话（同一份代码，独立审查）
  │   ├ CC#1: "请独立审查这份代码的逻辑漏洞"
  │   └ 模型B: 审查结果 → CC#1对比模型A的意见
  │
  ├ A和B意见一致 → 确认问题
  ├ A和B意见不一致 → CC#1追问双方 → 最终拍板
  │
  └ 将决策下达给CC#2执行
```

**这条流是skill v1.0最大的缺失**。v1.0的模块10只描述了"审查者A和B独立审查→汇合"，但没有描述CC#1作为**主动对话驱动者**的角色。

### 3.3 上下文保护机制（CC#2的核心价值）

```
CC#1 上下文预算：100%
├ 项目框架 + 决策记录  占用 ~30%
├ 当前阶段关键信息      占用 ~20%
└ 剩余留给决策思考      占用 ~50%

CC#2 上下文预算：100%
├ 完整代码               占用 ~40%
├ 运行日志 + 数据         占用 ~30%
├ 调试过程                占用 ~20%
└ 汇报精简                占用 ~10%

关键：CC#2吞掉所有"脏活"上下文，只把结论喂给CC#1
```

**CC#1绝对不做的**：
- 阅读完整源代码（交给CC#2和外部审查者）
- 逐行调试（交给CC#2）
- 阅读完整运行日志（CC#2提炼后汇报）
- 手动格式化数据（交给CC#2或文件提取者）

## 五、新增模块12：上下文保护机制

### 12.1 为什么需要

CC#1作为中枢大脑，上下文窗口是稀缺资源。如果CC#1的上下文被代码细节、运行日志、格式化操作占满，就会失去对项目全局的判断力。

### 12.2 分流规则

| 任务类型 | 谁来做 | 原因 |
|---------|--------|------|
| 代码编写(≤300行) | CC#2 | 常规任务 |
| 代码编写(>300行或高难度) | 外部模型→CC#2整合 | 分担复杂度 |
| 代码运行+测试 | CC#2 | 会产生大量日志 |
| 运行结果提炼 | CC#2提炼→CC#1 | CC#1只看结论 |
| PDF/图片数据提取 | 外部模型(Flash) | Claude Code读取受限 |
| 算法逻辑审查 | 外部模型(Pro) | 独立视角 |
| 论文审阅 | 外部模型(Pro) | 独立视角 |
| 最终决策 | CC#1 | 不可委托 |
| 项目框架+流程推进 | CC#1 | 核心职责 |

### 12.3 CC#1上下文告警

当CC#1感觉到以下信号时，说明上下文已被污染，需要立即将任务分流给CC#2：
- 阅读了超过50行代码
- 阅读了超过100行运行日志
- 手动调整了数据格式
- 重复执行了同一命令超过3次

### 12.4 CC#2汇报规范

CC#2向CC#1汇报时，必须使用以下精简格式：

```
【CC#2 → CC#1 阶段X 汇报】

完成：[做了什么]
结果：[关键数据摘要，不超过5行]
问题：[需要CC#1决策的事项]
原始输出：[保留在CC#2会话，需要时调取]
```

## 七、强制交叉审查（新增硬性规则）

### 规则

**任何重大任务结果在排版定档前，CC#1必须将结果提交给至少2个不同的外部AI模型进行独立分析。**

### 什么是"重大任务结果"

- 数学模型最终版（model.tex）
- 核心算法运行结果（最优方案）
- 论文正文初稿/终稿
- 交付给下游（如问题三）的CSV/数据文件
- 终审前的全部交付物

### 流程（不可跳过）

```
CC#1拍板某重大结果
       │
       ▼
┌──────────────────────────────┐
│  第1轮：提交给外部模型A       │
│  CC#1: "这是我们的XX结果，请独立分析"  │
│  模型A: 分析意见 + 漏洞发现 + 改进建议  │
├──────────────────────────────┤
│  第2轮：提交给外部模型B       │
│  CC#1: 同样的结果，独立分析    │
│  模型B: 分析意见（不与A交流）   │
├──────────────────────────────┤
│  第3轮（可选）：如果A和B意见   │
│  严重分歧，引入模型C打破平局   │
└──────────────────────────────┘
       │
       ▼
CC#1 综合分析：
  - A和B一致指出 → 必须修改
  - A和B分歧 → CC#1追问双方 → 研判 → 拍板
  - A指出B未指出 → CC#1研判 → 可采纳或驳回
  - 最终决定不可委托，必须CC#1做出
       │
       ▼
修改完成 → 定档
```

### CC#1的拍板权与约束

| CC#1有权 | CC#1必须 |
|---------|---------|
| 最终决定采纳哪些意见 | 收到至少2个外部模型的独立意见后**才能**拍板 |
| 驳回任何外部意见（需有理由） | 在决策记录中记录"采纳了X、驳回了Y、理由是Z" |
| 在A和B分歧时自行研判 | 分歧时不可跳过研判直接选A或B，必须追问双方向下挖 |

### 为什么这是硬性规则

本次C题项目的实际经验：
- Gemini Pro发现了"半日游"漏洞 → 如果当时没发给他审，论文会带着致命漏洞交上去
- A2排除问题 → 是CC#2运行后分析缓存发现的，如果只有CC#1一个人审可能漏掉
- 论文格式 + 三线表 + 公式排版 → 多个外部意见交叉才凑齐全部修改项

**单一AI的盲区是系统性的。只有多模型独立交叉才能逼近全覆盖。**

### 与模块4（阶段阀门）的关系

模块4的阀门规则不变。强制交叉审查是**阀门之前的最后一道关卡**——阀门打开前，必须先完成交叉审查。如果交叉审查未完成，阀门不可打开。
