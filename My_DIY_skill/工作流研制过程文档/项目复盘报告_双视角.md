## 二、代码演进复盘

### v1初版（328行，全排列枚举）
- **设计思路**：C(10,5)~C(10,8)景点组合 × 每天模式(d2,d1,d0) × n!排列 × 缓存过滤
- **核心问题**：全排列O(n!)架构在约束宽松时无法承受。修复午餐窗后缓存从14种暴增到101种（全可行），缓存过滤率从99.97%骤降，54M循环跑5小时
- **对的**：预计算日缓存(101种O(1)查表)是整个架构基石；午餐三策略覆盖全面
- **该换没换**：明知n=8时40K排列/组合太重，抱着"缓存能过滤"的侥幸没换方案

### v2重构（589行，递归回溯）
- **触发**：v1跑5小时才出结果，核心问题是生成再过滤 vs 直接构建
- **思路转变**：从"生成所有排列再过滤"变为"从剩余景点直接构建每天行程"，DFS天然匹配"每天选0/1/2个"的结构
- **效果**：枚举量从54M降至62K，运行时间从5小时降至165秒
- **教训**：枚举类问题直接写回溯，不要先全排列再优化

### 舒适时长切换（代码零改动）
- data.py把 `min_visit_time` 从最小游览时长改为舒适游览时长（如A1: 2.0→3.5）
- 结果是模型从6景点收敛到5景点，游览时间膨胀→可行域收缩→参数敏感性的诚实响应
- 这个结果反过来验证了TOPSIS对参数变化的合理响应——不是代码不稳，是约束真实收紧了

## 三、Bug清单与根因分析

| # | Bug | 发现阶段 | 发现方式 | 根因 | 教训 |
|---|-----|---------|---------|------|------|
| 1 | after_idx=-1午餐静默丢失 | 静态审查 | CC#1逐行审查 | 循环j从0开始，-1永不匹配 | 边界条件用枚举覆盖，-1/0/N三条路径都要有 |
| 2 | A2(偏好9.2)被无声排除 | 运行后分析 | CC#2检查缓存分布 | 策略3只搜空隙不搜边界+午餐窗约束过严 | 最高偏好景点必审；约束只约束该约束的东西 |
| 3 | 枚举性能爆炸 | 运行中 | v1跑了5小时 | 缓存全可行导致全排列内层丧失过滤 | 架构设计时考虑最坏情况，不要依赖过滤率假设 |
| 4 | 数据硬编码耦合 | 方案切换时 | stage3数据与stage2结果不一致 | 人工复制粘贴方案数据到两处 | 跨模块数据必须JSON透传 |

**核心发现**：bug#1和#2都是"不崩溃不报错，只是结果偏离"的无声bug。这是枚举+TOPSIS项目的最危险bug类型——约束逻辑的正确性只能靠审查+结果合理性分析双重验证。

**CC#2建议的静默bug检测机制**：
- 检查1：偏好-入选一致性（高偏好景点是否在Top-K中？若不在，是约束过严还是真的不可行？）
- 检查2：缓存覆盖率（高偏好景点单日不可行？→告警）
- 检查3：约束边界贴近度（某天距21:00有>8h空闲但景点数仍为1？→可能是约束过严）

## 五、架构教训

### 最大教训：数据流应该用JSON透传，不准硬编码

**现状**：stage2→终端输出→人工复制→stage3硬编码PLAN/SCHEDULE→改方案时改两处
**理想**：stage2→solution.json→stage3读取，stage5读取，问题三读取

**solution.json schema**（CC#2草案）：
```
{
  metadata: {timestamp, weights, lunch_window},
  recommended: {
    rank, topsis_score, objectives, attraction_ids,
    days: {
      "1": { attractions, total_time, timeline: [{step, type, start, end, duration, from, to, drive, attraction}], checks: {lunch_in_window, within_21, no_hotel_midway} }
    }
  },
  top3: [同结构]
}
```
下游全覆盖：stage3读timeline打印，stage3_gantt读timeline画色块，stage5读checks汇总，问题三读drive_h和duration_h注入扰动。

### 第二大教训：枚举类问题直接上回溯

不要走"先全排列再过滤"的弯路。DFS+早剪枝天然匹配组合约束问题。如果一开始就用递归回溯，v1→v2的重构轮次可以省掉。

## 九、可复用的通用框架提炼

### 通用多AI协作模式
```
任务拆解人(Gemini Pro) → 设计5阶段流程 + 数学模型
执行者(CC#2)          → 代码编写 + 运行 + 出图
审查者(CC#1)          → A/B/C分级审查 + 裁决 + 论文生成
协调者(MQTT)          → AI间信息传递 + 决策分发
```

### 通用审查分级制度
| 级别 | 适用 | 动作 |
|------|------|------|
| A级 | 核心算法、关键约束 | 逐行逻辑+边界条件+数学公式对齐 |
| B级 | 可视化、时序表 | 抽查关键逻辑+输出格式 |
| C级 | 调参重跑 | 只看输出+约束清单 |

### 通用阶段阀门
每个阶段出口必须通过审查才能进入下一阶段。阶段间设置同步加固触发点（4个）。

## 十、教训一句话总结

1. 枚举直接写回溯，别绕路
2. 数据用JSON透传，不准硬编码
3. 最高偏好景点必须出现在结果中，不在就是bug
4. 审查加"为什么"比"改什么"更有用
5. 静态审查在代码写完前就该介入（伪代码阶段）
