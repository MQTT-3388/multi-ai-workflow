# 多AI协作工作流 Skill — 完整设计规格（最终版 v1.0）

> 基于C题问题二项目全盘复盘提炼。底层通用框架，上层可叠加领域模板。
> 适用生态：本地API端（Claude Code） + 网页端（Gemini/GPT Web UI）混合协作。
> 合入：原始10模块 + Gemini 3轮审查反馈 + CC#2执行者复盘 + 深水区三问闭环。

---

## 一、总体架构

```
项目启动
  │
  ├ 0. 需求分析（brainstorming skill联动）
  │
  ├ 1. 角色定义 → 确定本次项目的AI分工及协作模式
  │
  ├ 2. 阶段规划 → 拆解任务为N个阶段，定义输入/输出/验收标准
  │
  ├ 3~N. 各阶段循环执行
  │    │
  │    ├── [高难度?]──是──→ 伪代码生成 → 网页端预审 → 通过→完整代码生成
  │    │    │                  (架构审查 + 复杂度评估 + 脑补极端case)
  │    │    └── 否 ──→ 直接生成代码
  │    │
  │    ├── 代码生成路由（竞赛/非竞赛分流 + 模型选择）
  │    ├── 多AI交叉审查（本地+网页双盲独立审查）
  │    ├── 常规审查分级（A/B/C）
  │    ├── 阶段阀门（通过→下一阶段 / 需修改→重审 / 驳回→重做）
  │    └── 同步加固（4个固定触发点 + 会话交接快照）
  │
  ├ N+1. 项目终审（全局交叉验证 + 静默bug检测）
  │
  └ N+2. 归档（6类目录结构 + 复盘报告）
```

## 二、模块详规

---

### 模块1：角色定义

**触发**：项目启动时

**内容**：定义本次项目的AI角色及其职责边界、协作模式（本地API / 网页端 / 混合）

```
┌──────────┬──────────────────────────────────┬─────────────────────────┐
│   角色   │              职责                │         禁止做          │
├──────────┼──────────────────────────────────┼─────────────────────────┤
│ 审查者   │ 审查验证、裁决争议、进度管理      │ 不写代码、不直接操作    │
│ (CC#1)  │ 终审、论文质量控制               │                         │
├──────────┼──────────────────────────────────┼─────────────────────────┤
│ 执行者   │ 编写代码、运行程序、生成图表      │ 不审查自己的输出         │
│ (CC#2)  │ 执行搜索、适配外部代码            │ 不自行裁决模型局限性     │
├──────────┼──────────────────────────────────┼─────────────────────────┤
│ 建模者   │ 数学模型设计、论文撰写/审阅       │ 不写完整代码             │
│ (Gemini) │ 算法逻辑分析、交叉审查            │ 不替代审查者的裁决职能   │
├──────────┼──────────────────────────────────┼─────────────────────────┤
│ 协调整合 │ AI间信息传递、决策分发            │ 不修改AI输出内容         │
│ (用户)   │ 最终确认所有交付物               │ 不跳过审查环节           │
└──────────┴──────────────────────────────────┴─────────────────────────┘
```

**协作模式声明**（启动时二选一）：
- `mode: "hybrid"` — 本地API端(Claude Code) + 网页端(Gemini/GPT Web UI)，适用模块11的混合协议
- `mode: "api_full"` — 全部通过API调用，自动化程度最高

### 模块2：阶段规划

**触发**：角色定义完成后

**内容**：将项目任务拆解为线性阶段（3~7个为宜）

```
┌──────┬──────────┬──────────┬──────────┬──────────────┐
│ 阶段 │   名称   │   输入   │   输出   │   验收标准   │
├──────┼──────────┼──────────┼──────────┼──────────────┤
│  1   │  数据    │ 原始资料 │ 结构化数据│ 格式+完整性  │
│  2   │  模型    │ 数据+需求│ 数学模型 │ 公式正确性   │
│  .   │          │          │          │              │
│  N   │  交付    │ 全部产出 │ 打包文件 │ 清单核对     │
└──────┴──────────┴──────────┴──────────┴──────────────┘
```

**规则**：
- 每阶段必须有可量化的验收标准
- 每阶段指定唯一的审查者
- 独立子任务可并行启动（如论文可与代码并行），但需在阀门处等待确认
- 跨阶段数据必须通过结构化文件（JSON/CSV）传递，禁止人工复制粘贴

---

### 模块3：审查分级（A/B/C）

| 级别 | 适用场景 | 审查内容 | 时间预算 |
|------|---------|---------|---------|
| **A级** | 核心算法、关键约束逻辑、数据模块 | 逐行逻辑审查 + 边界条件 + 公式对齐 + 静默bug扫描 | 30~60min |
| **B级** | 可视化、时序生成、格式转换 | 抽查关键逻辑 + 输出格式 + 与上游数据一致性 | 10~20min |
| **C级** | 调参重跑、小修小改、最终确认 | 约束检查清单 + 输出数值合理性 | 5~10min |

**A级审查清单**：
- [ ] 所有约束是否被代码覆盖（逐条对照模型公式）
- [ ] 边界条件：0值、max值、空集、-1索引
- [ ] 静默bug扫描：高优先级项是否在结果中出现
- [ ] 循环/递归终止条件是否完备
- [ ] 数据依赖是否正确（变量名、索引范围、数据类型）

**B级审查清单**：
- [ ] 输出格式是否符合约定
- [ ] 与上游数据是否一致（通过读JSON/CSV校验）
- [ ] 可视化元素完整（标签、图例、配色、DPI）
- [ ] 关键数值在合理范围

**C级审查清单**：
- [ ] 终审硬约束逐条核验
- [ ] 输出数值与预期一致

**审查者模型分配**：
| 审查级别 | 首选模型 | 
|---------|---------|
| A级（算法正确性） | Gemini 3.1 Pro / Claude Opus / GPT 5.5 |
| A级（业务约束） | CC#1 本地端 |
| B/C级 | Gemini 3.1 Flash / Claude Haiku |

**核心原则：代码生成者和审查者不能是同一个模型。**

---

### 模块4：阶段阀门

```
if 审查结果 == "通过":
    → 进入下一阶段
elif 审查结果 == "需修改":
    → 执行者修改 → 重审（最多3轮）
    → 3轮仍不通过 → 升级到人工裁决
else:
    → 本阶段重做
```

**不允许**：跳过审查直接进入下一阶段、连续4轮修改仍不裁决、前阶段未通过就启动后阶段。

---

### 模块5：同步加固

**触发时机**：阶段间切换时（4个固定点：数据就位后→核心产出后→交付前→终审前）

**加固内容**：
1. 双方确认当前阶段产出物清单及状态
2. 确认下一阶段输入/输出/验收标准
3. 检查未裁决分歧
4. 生成会话交接快照
5. **下游代码入口必须包含防御性断言（Assert Guards）**

**防御性断言要求**（防数据契约流于形式）：
```python
# 下游阶段代码入口必须包含
assert "recommended" in data, "契约失效：未找到recommended节点"
assert len(data["recommended"]["days"]) == 5, "数据异常：天数≠5"
# 物理量单位校验
assert all(isinstance(v, float) for v in drive_times), "车程单位异常"
```

**跨阶段数据契约**：任何跨阶段切换，输出方必须提供结构化数据文件（JSON/CSV），下游必须通过读取该文件获取数据，禁止硬编码。

---

#### 会话交接快照模板

每次阶段切换或更换AI会话时，CC#1必须生成此快照。用户一键复制到新会话首条Prompt。

**混合模式版（本地→网页端）**：
```markdown
【网页端审查冷启动快照】
1. 当前上下文
   - 目标阶段：[Stage X (算法实现) A级审查]
   - 依赖文件：[data.py (数据源), main.py (核心算法)]

2. 数据契约（云端大脑必读）★
   - 外部变量格式：[如 data.py 中 min_visit_time 为 Dict, key为'A1'~'A10']
   - 物理单位基准：[时间=小时(float), 距离=公里(float)]
   - 核心约束规则：[如 午餐开始∈[11:00,14:00], 7:00-21:00活动窗]

3. 本次审查任务 ★
   - [请对以下代码进行独立静态审查。重点：边界条件、时间复杂度、约束覆盖。]

4. 防遗忘核验（接棒AI必读）★
   - [ ] 确认输入数据的物理单位与上游一致
   - [ ] 确认未在代码中重新硬编码上游已锁定的变量
```

**本地模式版（CC#1↔CC#2）**：
```markdown
【工作流交接快照】
- 当前阶段：Stage X
- 锁定产出：[已确认文件/版本]
- 数据契约：[变量名/格式/单位/索引]
- 遗留分歧：[待裁决]
- 本次任务：[接棒AI具体动作]
- 验证标准：[运行命令+预期输出]
```

### 模块6：项目终审

**触发**：所有阶段阀门通过后

**6.1 全局硬约束核验**
- [ ] 逐条对照题目/需求文档的全部硬约束
- [ ] 上下游数据一致性（输出CSV能否被下游正确读取）

**6.2 静默bug检测**（自动脚本 + 人工研判）
- 检查1：偏好-入选一致性。高偏好项是否在Top-K中出现？若不在→是约束过严还是真不可行？
- 检查2：缓存覆盖率。高偏好景点的单日行程是否可行？
- 检查3：约束边界贴近度。是否存在异常大的余量（>8h空闲但景点数=1）→可能是约束过严
- 检查4：交付物完整性。清单文件是否都存在且非空

**6.3 跨模块逻辑闭环**
- [ ] 模块间假设一致
- [ ] 数据流转正确（输入→处理→输出→下游输入）
- [ ] 论文数据与运行结果一致

**6.4 交付物清单核对**

**通过标准**：6.1全通过 + 6.2无告警 + 6.3无矛盾 + 6.4齐套

### 模块9：代码生成路由

#### 高难度判定阈值（客观标准，满足任一即触发）

| # | 条件 |
|---|------|
| 1 | 涉及递归、回溯、DP、启发式搜索、图论算法 |
| 2 | 约束条件 ≥ 3个 或 目标函数 ≥ 2个 |
| 3 | 时间复杂度预估 ≥ O(N·M) 且 N ≥ 1000 |
| 4 | 需要操作外部优化求解器（gurobi、scipy.optimize等） |

#### 路径分流

```
触发高难度阈值?
  ├ 是 → 伪代码生成 → 网页端伪代码预审 → 通过 → 完整代码生成
  │       预审内容：复杂度评估 + 脑补极端case推演 + 架构合理性
  └ 否 → 直接生成完整代码

选择生成AI（按任务难度）：
├ 高难度算法 → GPT 5.5 / Gemini 3.1 Pro / DeepSeek-v4
├ 中等逻辑   → Gemini 3.1 Pro / Claude Sonnet
├ 简单脚本   → Gemini 3.1 Flash
└ 可视化     → 执行者直接写（B级审查）

竞赛模式：输入=算法思路（非源代码），独立生成
非竞赛模式：
├ 外部代码质量高 → 稍改复用
├ 外部代码质量低 → 提取思路 → AI重写
└ 无外部参考     → 制定需求文档 → AI从零生成
```

---

#### 伪代码审查清单（网页端负责，主攻"架构性灾难"）

| 审查维度 | 具体内容 |
|---------|---------|
| 复杂度评估 | 以输入规模N=10到N=1000为边界，推导最坏时间复杂度。若达到10^6次以上枚举，驳回并建议重构 |
| 剪枝合理性 | 剪枝策略是否会误剪可行解？ |
| 收敛性 | 是否存在无法终止的无限递归？ |

**脑补运行机制（Dry-Run Simulation）**：
审查者必须手动推演以下3种极端输入，给出推演路径：

| 极端case | 检查点 |
|----------|--------|
| 极小边界 | 景点数=0或1时，算法是否返回空/单点方案而非崩溃 |
| 极严约束 | 所有景点均不可行时（如游览时长>开放窗口），是否快速返回无解而非死循环 |
| 退化输入 | 所有偏好值相同、或所有距离相同时，评价机制是否因分母为0而崩溃 |

### 模块10：多AI交叉审查

#### 标准模式（多模型可用）

```
代码就绪
  ↓
┌─────────────────────────────────────────────┐
│ 审查者A（建模者，网页端Gemini Pro）           │
│ - 只给代码 + 需求描述 + 数据契约              │
│ - 不给CC#2上下文                             │
│ - 审查：算法正确性、复杂度、边界处理           │
├─────────────────────────────────────────────┤
│ 审查者B（执行审查者，本地CC#1）               │
│ - 结合项目完整上下文                          │
│ - 审查：项目约束匹配、参数一致性、模块对接     │
└─────────────────────────────────────────────┘
  ↓
┌─────────────────────────────────┐
│ 汇合：                           │
│ 两人都通过    → ✅ 通过           │
│ 两人都告警    → 🐛 确认bug        │
│ 仅一人告警    → ⚠️ 研判盲区       │
└─────────────────────────────────┘
```

**审查者A必须附带运行日志**：
代码提交审查时，执行者必须同时提交：
- 运行命令
- 完整终端输出（含耗时、中间变量值）
- 生成的输出文件
审查者结合静态代码+动态运行日志同时研判。

#### 降级模式（仅单一模型可用）

若用户只有一个模型的API/会话额度，启用降级策略：

| 环节 | 操作 |
|------|------|
| 生成时 | 标准温度(0.5)，System Prompt="执行者" |
| 审查时 | 新建独立会话，温度=0，System Prompt="冷酷的静态审计员。唯一职责是寻找Bug和逻辑漏洞。禁止输出可运行代码，只能指出问题。" |
| 隔离 | 生成和审查必须在不同会话Tab中进行，上下文完全清零 |

**降级标注**：结果中标注 `[降级审查] 本次因资源限制使用同模型审查，建议在条件允许时切换多模型交叉验证。`

### 模块11：混合模式手动降级协议

> 适用场景：本地API端(Claude Code) + 网页端(Gemini/GPT Web UI) 协作。

#### 11.1 本地一键Dump机制

需要网页端审查时，本地端执行：
```bash
cat data.py main.py output.log > review_payload.txt
```
用户打开 `review_payload.txt`，Ctrl+A 复制，一次性贴给网页端AI。消灭碎片化复制粘贴。

#### 11.2 网页端硬隔离规则

| 规则 | 说明 |
|------|------|
| Tab隔离 | 网页端审查必须在**全新的浏览器Tab**（无历史聊天记录）中进行 |
| 角色锁死 | 新Tab首句Prompt必须使用角色锁定词 |
| 禁止回看 | 不与之前的对话共享上下文，防止"自证幻觉" |

**角色锁死Prompt模板**：
```
你现在是冷酷的静态审计员。你的唯一职责是寻找代码中的Bug和逻辑漏洞。
在接下来的对话中，禁止输出任何可直接运行的代码，只能指出问题所在。
如果你违反，将导致我的项目崩溃。请确认你的职责。
```

#### 11.3 用户作为无损中继

用户在不同AI之间传递信息时：
- 禁止对代码做任何人工修改
- 禁止添加自己的解读或暗示
- 原样复制粘贴

## 三、完整执行流程图

```
                          项目启动
                             │
                    ┌─ 需求分析(brainstorming)
                    └─────┬──────┘
                          │
                    ┌─ 角色定义(模块1, 选模式)
                    └─────┬──────┘
                          │
                    ┌─ 阶段规划(模块2)
                    └─────┬──────┘
                          │
              ╔═══════════╧═══════════╗
              ║   阶段N循环 (N=1~M)   ║
              ║                       ║
              ║  是否需要写代码？      ║
              ║   ├ 是                ║
              ║   │  ├ 高难度? → 伪代码 → 网页预审(脑补3case) → 通过
              ║   │  ├ 外部搜索(模块8, 竞赛/非竞赛分流)
              ║   │  ├ 代码生成路由(模块9, 模型分配)
              ║   │  ├ 多AI交叉审查(模块10, 标准/降级)
              ║   │  └ 混合模式Dump(模块11)
              ║   │        ↓           ║
              ║   └ 否                 ║
              ║         ↓              ║
              ║   ┌─ 常规审查(A/B/C) ─┐ ║
              ║   └─────┬─────────────┘ ║
              ║         ↓               ║
              ║   ┌─ 阶段阀门(模块4) ──┐ ║
              ║   └─────┬─────────────┘ ║
              ║    通过↓               ║
              ║   ┌─ 同步加固(模块5) ──┐ ║
```

## 五、核心假设与适用边界

### 适用条件
1. 角色可分：审查者与执行者必须是两个独立AI实例
2. 标准可量化：每个阶段必须有"通过/不通过"的客观判断标准
3. 时间允许迭代：剩余时间≥4小时

### 不适用场景
1. 单人（单AI）项目：无交叉验证价值
2. 实时交互型调试：审查延迟不可接受
3. 高度探索性任务：无明确验收标准
4. 需求持续剧烈变动：同步频率跟不上

### 最大收益场景
- 有明确硬约束的工程优化项目
- 多模块协作的复杂系统
- 竞赛/学术等对正确性极高的场景
- 需要多轮迭代的创意产出

### 降级底线
- 最恶劣条件（纯网页端+仅单一模型+隔夜冷启动）：模块11硬隔离协议 + 会话交接快照 + 降级审查策略仍可支撑工作流运转
- 不可降级的原则：审查与执行必须隔离、阀门不可跳过、终审不可省略
