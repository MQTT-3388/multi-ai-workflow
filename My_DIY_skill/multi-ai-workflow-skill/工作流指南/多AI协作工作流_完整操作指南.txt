================================================================
  一、工作流概述
================================================================

  这套工作流解决什么问题？
  ---------------------------------
  当你一个人用多个AI（Claude Code、Gemini、GPT等）协作完成
  一个复杂项目时，会遇到这些问题：

  1. AI写的代码自己查不出bug（因为生成代码的AI和审查代码
     的AI是同一个模型，他们共享相同的盲区）
  2. 中枢AI的上下文被大量代码细节和调试日志淹没，失去
     对项目全局的判断力
  3. 不同AI之间的信息传递混乱，格式不统一，数据不一致
  4. 缺乏强制性的质量阀门，错误累积到最后才被发现

  这套工作流通过"星型中枢 + 强制交叉审查 + 上下文隔离"
  三个机制，系统性地解决以上全部问题。

  这套工作流不是什么？
  ---------------------------------
  - 不是一个自动运行所有AI的脚本
  - 不是一个让你不用动脑的自动化工具
  - 不适用于30分钟内能完成的简单任务

  它是一套经过实战验证的"人机协作工程学协议"——告诉你
  在不同的阶段用什么AI、怎么审查产出、怎么传递信息、怎么
  做最终决策。

  二、核心功能清单（v2.1）
================================================================

  项目协作
  ├ 多AI角色分工（CC#1中枢 + CC#2副手 + 外部模型5类）
  ├ 阶段化项目拆解（3~7阶段·输入/输出/验收标准）
  ├ 任务路由决策（代码/审查/提取/决策 → 不同AI）
  └ Skill联动（17个superpowers skill深度/中度/轻度集成）

  质量保障
  ├ A/B/C/D四级审查（控制流→格式→清单→跨模型交叉）
  ├ 阶段阀门（通过/修改≤3轮/驳回）
  ├ 强制交叉审查（≥2轮独立·3层降级）
  ├ 伪代码预审（高难度算法·3个极端case脑补运行）
  └ 防御性断言（Assert Guards + JSON Schema契约）

  上下文管理（v2.1四层防御）
  ├ L1·CC#2分流：代码/日志/调试→CC#2，CC#1只看信号
  ├ L2·告警信号：CC#1(退化/回看/跨阀门) CC#2(倾倒日志/反复修改/失忆)
  ├ L3·检查点切换：写入项目状态_当前.md→新会话→恢复
  └ L4·磁盘快照：关机/崩溃→从文件冷恢复

  断点恢复（v2.1检查点系统）
  ├ 项目状态_当前.md — 磁盘唯一真相源·模型无关
  ├ 关机恢复：5分钟关机协议→30秒恢复
  ├ 上下文切换：安全切换点规则（决策完成后·非讨论中途）
  ├ CC#2自我切换：不等决策·存盘→更新→新会话→汇报
  └ 阶段回溯：git tag + .workflow_history/ + 原子回溯指令

  信息传递
  ├ CC#2→CC#1精简汇报格式（只呈报信号·不倾倒噪声）
  ├ CC#2自动生成handoff_payload.txt（快照+代码+日志一键复制）
  ├ 网页端Tab硬隔离（新Tab+角色锁死+零上下文）
  └ 用户只读中继协议（只复制粘贴·不改代码·不加解读）

  降级容灾
  ├ 审查降级：标准级(2异构)→会话级(1模型2轮)→单点级(自审)
  ├ 维护防疲劳：CC#1自动输出检查点·CC#2每次产出存盘
  ├ 崩溃恢复：项目状态_当前.md + git commit 双重保险
  └ 防幻觉：保存前10秒人眼Review检查点


================================================================
  三、核心理念：为什么需要这套方法
================================================================

  理念1：AI有系统性盲区，单模型审查不可靠
  ---------------------------------
  同一个AI模型在生成代码和审查代码时，会基于相同的推理
  路径和知识盲区。它"看不出来"自己的问题。

  真实案例（C题项目）：
  - Gemini Pro发现了CC#1和CC#2都没发现的"半日游"逻辑漏洞
  - A2景点的排除问题是CC#2分析运行结果发现的，不是代码报错
  - 论文格式+三线表+公式排版，3个外部意见交叉才凑齐全部修改项

  解决方案：强制交叉审查。任何重大结果在定稿前，必须经
  过至少2轮独立的外部AI审查。

  理念2：上下文是AI最稀缺的资源
  ---------------------------------
  AI的"注意力"有限。如果CC#1（决策中枢）的上下文被500行
  代码、300行运行日志、50行报错信息填满，它就无法做出
  正确的全局判断。

  解决方案：CC#2作为"噪声吞噬者"——在自己的独立会话中
  处理所有代码编写、运行、调试、日志阅读，只把精简结论
  汇报给CC#1。CC#1只需要知道"通过了/没通过/卡在哪了"，
  不需要知道每一个语法错误的细节。

  理念3：错误会累积，阀门必须在早期拦截
  ---------------------------------
  没有质量阀门的项目，前期的小错误会在后期滚成大雪球。

  解决方案：每个阶段结束时设置硬性阀门——审查不通过，
  不允许进入下一阶段。最大3轮重审，还不过就升级到人工
  裁决，而不是"算了先跳过"。


================================================================
  四、架构详解：三个角色如何协作
================================================================

  整体架构
  ---------------------------------

                ┌──────────────────────┐
                │   CC#1（中枢大脑）     │
                │  推进·审核·决策·拍板   │
                └────┬─────────┬───────┘
                     │         │
        ┌────────────┘         └────────────┐
        ▼                                   ▼
  ┌─────────────┐                 ┌──────────────────┐
  │ CC#2（副手） │                 │  外部模型群(5类)  │
  │ 执行·同步   │                 │ 算法·审查·审阅    │
  │ 吞噬噪声    │                 │ 提取·需求         │
  │ 保护CC#1   │                 │ 多视角独立验证     │
  └─────────────┘                 └──────────────────┘

  CC#1 — 中枢大脑（你的主Claude Code会话）
  ---------------------------------
  这是你项目的主控台。CC#1负责：
  - 制定项目阶段计划
  - 向CC#2分发执行任务
  - 向外部模型发起审查对话
  - 综合所有外部意见，做出最终拍板
  - 推进项目节奏，确保不偏航

  CC#1不做什么：
  - 不逐行阅读完整代码（交给CC#2和外部审查者）
  - 不亲自调试程序（交给CC#2）
  - 不手动格式化数据（交给CC#2或外部模型）
  - 不沉浸在"这个变量为什么是3而不是4"的细节中

  识别你正在违反CC#1原则的信号：
  - 你在逐行读代码（而非看控制流和设计逻辑）
  - 你在手动调格式（而非审整体架构）
  - 你在反复执行同一命令调试同一个bug
  出现以上信号 → 立即把任务分流给CC#2

  CC#2 — 核心副手（另一个独立的Claude Code会话）
  ---------------------------------
  CC#2存在的首要意义不是"写代码"，而是"保护CC#1的上下文
  不被污染"。它在自己的独立会话中承接所有"脏活"：

  - 代码编写（≤300行的常规任务）
  - 代码运行和测试
  - 阅读和解析运行日志
  - 生成图表（甘特图、流程图等）
  - 将外部模型生成的高难度代码整合到项目中
  - 在本地执行所有文件操作

  CC#2向CC#1汇报的格式：
  【CC#2 → CC#1 阶段X汇报】
  完成：[做了什么]
  结果：[关键数据摘要，不是整个日志]
  问题：[需要CC#1决策的事项]
  原始输出：[保留在CC#2会话，需要时调取]

  CC#2的原则：只呈报信号，不倾倒噪声。

  外部模型群 — 你的多功能工具包
  ---------------------------------
  这些是你通过浏览器网页端调用的AI模型（Gemini、GPT等）。
  它们不是"一个角色"，而是按需调用的5类工具：

  ┌──────────────┬──────────────────────┬──────────────────┐
  │    工具类型  │       做什么         │    建议模型      │
  ├──────────────┼──────────────────────┼──────────────────┤
  │ 算法生成者   │ 高难度算法/伪代码    │ GPT 5.5/Gemini   │
  │              │ 复杂度分析           │ 3.1 Pro          │
  ├──────────────┼──────────────────────┼──────────────────┤
  │ 代码审查者   │ 独立审查CC#2的代码   │ Gemini 3.1 Pro   │
  │              │ 发现逻辑漏洞         │ / Claude Opus    │
  ├──────────────┼──────────────────────┼──────────────────┤
  │ 论文审阅者   │ 审阅论文初稿/终稿    │ Gemini 3.1 Pro   │
  │              │ 发现逻辑漏洞和格式    │                  │
  ├──────────────┼──────────────────────┼──────────────────┤
  │ 文件提取者   │ 提取PDF/图片等       │ Gemini 3.1 Flash │
  │              │ CC无法直接读的数据    │                  │
  ├──────────────┼──────────────────────┼──────────────────┤
  │ 需求提炼者   │ 模糊需求→结构化文档  │ Flash /          │
  │              │ 初步流程框架          │ CC#1自带的模型   │
  └──────────────┴──────────────────────┴──────────────────┘

  最少配置（能跑起来的底线）：CC#1 + CC#2 + 1个外部模型 = 3个窗口

  用户（你）— AI之间的数据桥梁
  ---------------------------------
  你在混合模式下（本地API + 网页端）承担了"数据总线"的角色。
  你的核心规则只有一条：只读中继。

  - 把CC#1的任务转给CC#2 → 原样传递，不加自己的理解
  - 把CC#2的结果带回CC#1 → 原样传递，不手动修改
  - 把CC#1指定的内容发给外部模型审查 → 原样传递
  - 把外部模型的意见带回CC#1 → 原样传递

  你绝对不做的：手动改动任何一个AI产出的代码或文本。
  如果代码需要修改，告诉CC#2去改。你只负责"复制粘贴"。


================================================================
  五、项目启动：从零开始搭建
================================================================

  步骤1：判断是否适合用工作流
  ---------------------------------
  问自己三个问题：
  ① 项目能拆成3~7个独立的步骤吗？
  ② 每个步骤有明确的"完成/没完成"判断标准吗？
  ③ 预计总时间 ≥ 4小时吗？

  三个都回答"是" → 继续下一步。
  任何一个"否" → 不适合用这套工作流，用普通对话模式。

  步骤2：在主会话启动工作流
  ---------------------------------
  对你的主Claude Code（CC#1）说：

  "启动多AI工作流。
   项目类型：数学建模（或 软件开发/数据分析/学术论文）。
   协作模式：hybrid（本地API + 网页端）。
   项目简介：[用2-3句话描述你要做什么]"

  CC#1会自动执行：
  - 定义三个角色的具体分工
  - 根据项目类型拆解阶段
  - 输出完整的项目框架（每个阶段的输入/输出/验收标准）
  - 告诉你需要开几个外部窗口

  步骤3：配置CC#2（第二个Claude Code会话）
  ---------------------------------
  打开一个新的Claude Code窗口，输入：

  "你是CC#2副手。你的首要职责是保护CC#1的上下文不被污染。
   你需要承接代码编写、脚本运行、测试执行、数据生成、
   图表绘制等所有执行任务。

   结果向CC#1汇报时使用精简格式：
   【CC#2 → CC#1 阶段X汇报】
   完成：[做了什么]
   结果：[关键数据摘要]
   问题：[需要CC#1决策的事项]
   原始输出：[保留在本会话]

   确认你的职责，等待CC#1下达第一个任务。"

  CC#2确认后，把项目框架文档发过去，让它了解全貌。

  步骤4：配置外部审查窗口
  ---------------------------------
  打开浏览器，新建一个无痕/隐私窗口（确保无历史上下文）。

  在这个新Tab中打开Gemini/GPT网页版，第一条消息粘贴：

  "你现在是冷酷的静态审计员。你的唯一职责是寻找代码中
   的Bug和逻辑漏洞。在接下来的对话中，禁止输出任何可直接
   运行的代码，只能指出问题所在。如果你违反，将导致我
   的项目崩溃。请确认你的职责。"

  这个Tab就是你的"代码审查者"。之后每次需要审查时，
  都重新开一个新的Tab（不要复用旧的，防止上下文污染）。

  同样的方式，再开一个Tab配置"论文审阅者"，把角色锁定
  词的"Bug和逻辑漏洞"改为"论文中的逻辑漏洞、格式问题和
  论证缺陷"。


================================================================
  六、日常执行：每个阶段怎么跑
================================================================

  一个阶段的完整生命周期
  ---------------------------------

  ┌─────────────────────────────────────────────────┐
  │  1. CC#1 下发任务                                │
  │     "CC#2，阶段2任务：用data.py的数据，编写核心   │
  │     优化算法。约束条件见模型公式(1)-(25)。         │
  │     输出：stage2_optimization.py + 运行结果。"     │
  ├─────────────────────────────────────────────────┤
  │  2. CC#2 执行                                    │
  │     在自己的会话中写代码、调试、运行。              │
  │     可能会来回跑好几轮，都在CC#2会话内消化。        │
  ├─────────────────────────────────────────────────┤
  │  3. CC#2 精简汇报给CC#1                          │
  │     【CC#2 → CC#1 阶段2汇报】                     │
  │     完成：stage2_optimization.py (589行)           │
  │     结果：最优方案6景点，TOPSIS得分0.8085          │
  │     问题：A2景点被排除，是否修复？                 │
  ├─────────────────────────────────────────────────┤
  │  4. CC#1 审查                                    │
  │     根据任务难度选择A/B/C级审查：                  │
  │     A级（核心算法）：控制流+边界+公式验证           │
  │     B级（图表/格式）：抽查逻辑+输出格式             │
  │     C级（调参重跑）：核对清单                       │
  ├─────────────────────────────────────────────────┤
  │  5. 如果是重大结果 → 触发强制交叉审查              │
  │     CC#1: "准备交接给外部审查"                     │
  │     CC#2: 生成 handoff_payload.txt                │
  │     你: 复制到网页端外部模型 → 拿回审查意见          │
  │     CC#1: 综合外部意见 + 自己的判断 → 裁决          │
  ├─────────────────────────────────────────────────┤
  │  6. 阶段阀门                                      │
  │     ✅ 通过 → 进入下一阶段                         │
  │     ⚠️ 需修改 → CC#2改 → 重审（最多3轮）         │
  │     ❌ 驳回 → 重做本阶段                          │
  ├─────────────────────────────────────────────────┤
  │  7. 同步加固                                      │
  │     双方确认产出物 + 更新交接快照 + 确认下阶段      │
  │     输入输出标准 → 进入下一阶段                    │
  └─────────────────────────────────────────────────┘

  审查级别速查表
  ---------------------------------
  ┌──────┬──────────────┬──────────────────┬──────────┐
  │ 级别 │    适用      │      做什么      │   耗时   │
  ├──────┼──────────────┼──────────────────┼──────────┤
  │ A级  │ 核心算法     │ 控制流验证       │ 30-60min │
  │      │ 关键约束     │ +边界推演        │          │
  │      │ 数据模块     │ +设计契约审计    │          │
  ├──────┼──────────────┼──────────────────┼──────────┤
  │ B级  │ 可视化       │ 抽查逻辑         │ 10-20min │
  │      │ 时序表       │ +输出格式验证    │          │
  │      │ 格式转换     │ +数据一致性      │          │
  ├──────┼──────────────┼──────────────────┼──────────┤
  │ C级  │ 调参重跑     │ 约束清单核对     │ 5-10min  │
  │      │ 小修小改     │ +数值合理性      │          │
  ├──────┼──────────────┼──────────────────┼──────────┤
  │ D级  │ 跨模型交叉   │ 外部AI独立审查   │ 按需     │
  │      │              │ (算法/论文/数据) │          │
  └──────┴──────────────┴──────────────────┴──────────┘

  任务路由：谁做什么
  ---------------------------------
  CC#1收到一个任务时，按以下逻辑判断交给谁：

  需要写代码？
  ├ 是 → ≤300行且非高难度 → CC#2写
  │     >300行或高难度  → 外部模型生成 → CC#2整合到项目
  ├ 需要审查产出？ → 外部模型独立审 → CC#1综合
  ├ 需要提取PDF/图片数据？ → 外部模型（Flash）
  └ 需要最终决策？ → 只有CC#1能做

  什么算"高难度算法"（满足任一即触发）：
  - 涉及递归、回溯、动态规划、启发式搜索、图论算法
  - 约束条件≥3个 或 目标函数≥2个
  - 预估时间复杂度 ≥ O(N×M) 且输入规模N≥1000
  - 需要使用外部优化求解器（gurobi、scipy.optimize等）

  高难度算法在正式写代码前，必须先做伪代码预审：
  1. 外部模型生成伪代码
  2. CC#1审查3个极端case（极小输入/极严约束/退化输入）
  3. 通过后才生成完整代码


================================================================
  七、强制交叉审查：最核心的规则
================================================================

  什么结果必须交叉审查
  ---------------------------------
  以下5类结果在最终定档前，必须经过外部交叉审查：

  1. 数学模型最终版（如model.tex）
  2. 核心算法运行结果（最优方案、Top-K）
  3. 论文正文初稿和终稿
  4. 交付给下游的数据文件（如CSV基准行程）
  5. 终审前的全部交付物

  一句话判断标准：如果这个结果错了，会导致后面的工作全部白做
  或论文出现致命漏洞——那就必须交叉审查。

  审查的三个层级（自动选择最高可用的）
  ---------------------------------

  ┌────────┬──────────────┬──────────────────────────┐
  │  层级  │    条件      │         怎么做           │
  ├────────┼──────────────┼──────────────────────────┤
  │ 标准级 │ 有2个不同    │ Gemini独立审 + GPT独立审 │
  │  (最优) │ 的外部模型   │ 两份意见独立，不互通      │
  │        │              │ CC#1对比两份意见后综合    │
  ├────────┼──────────────┼──────────────────────────┤
  │ 会话级 │ 只有1个      │ 用同一个模型做2轮独立审查 │
  │  (降级) │ 外部模型     │ 第1轮：新Tab+角色锁定     │
  │        │              │ 第2轮：重新开新Tab        │
  │        │              │ 两次审查独立，CC#1对比     │
  ├────────┼──────────────┼──────────────────────────┤
  │ 单点级 │ 没有外部     │ CC#1和CC#2自行审查        │
  │  (应急) │ 模型可用     │ 终审时必须标注             │
  │        │              │ [单模型审查·风险自担]     │
  └────────┴──────────────┴──────────────────────────┘

  CC#1如何综合多方意见
  ---------------------------------
  收到两份（或多份）外部审查意见后：

  ┌──────────────────────────────────────────────┐
  │ 情况1：两个模型一致指出某个问题                │
  │ → 必须修改，不需要犹豫                         │
  ├──────────────────────────────────────────────┤
  │ 情况2：两个模型意见严重分歧                    │
  │ → CC#1向双方追问细节                           │
  │ → 深挖分歧的根因（是定义不同？还是逻辑不同？）    │
  │ → CC#1研判后做出裁决                           │
  ├──────────────────────────────────────────────┤
  │ 情况3：模型A指出、模型B没指出                  │
  │ → CC#1独立研判                                │
  │ → 可采纳（分析有理）或驳回（与项目约束冲突）     │
  │ → 驳回必须写明理由                              │
  ├──────────────────────────────────────────────┤
  │ 最终决策                                       │
  │ → 不可委托，必须CC#1自己做出                    │
  │ → 记录："采纳了X的建议、驳回了Y的建议、         │
  │          理由是Z、存疑待观察的是W"              │
  └──────────────────────────────────────────────┘

  为什么这是硬性规则（不可跳过）
  ---------------------------------
  真实经历：
  - C题项目中，Gemini Pro发现了"半日游"漏洞——如果当时没发
    给外部模型审，论文会带着致命漏洞交上去
  - A2景点（喜好度9.2最高）被排除——CC#2分析运行结果时发现
    的，如果只有CC#1一个人审，大概率漏掉
  - 论文格式 + 三线表 + 公式排版 → 来自3个不同AI的意见交叉
    才凑齐了全部需要修改的项

  单一AI的盲区是系统性的，不是偶然的。只有多模型独立交叉审查
  才能逼近全覆盖。


================================================================
  十、交接与同步：信息如何传递
================================================================

  情况A：CC#1分派任务给CC#2
  ---------------------------------
  直接把CC#1的指令复制给CC#2。包含：
  - 当前处于哪个阶段
  - 本次任务的具体要求
  - 输入文件在哪里（路径）
  - 预期输出是什么
  - 验收标准是什么

  CC#2执行完后，按精简格式汇报回CC#1。

  情况B：把产出交给外部模型审查
  ---------------------------------
  这是摩擦最大的环节。为了减少你的操作负担：

  第1步：在CC#1会话中，CC#1说"准备交接给外部审查"

  第2步：CC#2在你本地自动生成 handoff_payload.txt
         这个文件自动合并了：
         - 交接快照（阶段说明/数据契约/审查任务）
         - 待审查的完整代码
         - 运行日志摘要
         - 核心变量值/输出结果

  第3步：你打开 handoff_payload.txt
         Ctrl+A 全选 → Ctrl+C 复制

  第4步：打开浏览器新Tab（必须是新的，无历史）
         粘贴 → 发送给外部模型

  第5步：外部模型返回审查意见
         你 Ctrl+A 复制 → 带回CC#1会话粘贴

  第6步：CC#1阅读审查意见 → 综合分析 → 做出裁决
         → 如需修改，下达给CC#2执行

  关键纪律：
  - 每次外部审查都必须新建浏览器Tab（防止上下文粘性导致
    外部模型"懒得审"）
  - 你只做复制粘贴，不在传递过程中加自己的理解或修改
  - 如果需要发给2个外部模型审查（标准级），必须开2个独立
    的Tab，两个模型不能看到对方的意见

  情况C：阶段结束时的同步加固
  ---------------------------------
  以下4个时间点必须做双向同步：
  1. 数据就位后（确认data.py等数据文件锁定）
  2. 核心产出完成后（确认运行结果通过审查）
  3. 交付打包前（确认全部交付物清单）
  4. 终审前（最终对齐所有决策记录）

  同步加固时CC#1和CC#2互相确认：
  - 本阶段的产出物清单是否完整
  - 下一阶段的输入输出标准是否有变化
  - 有没有还没裁决的分歧
  - 数据契约（变量名/格式/单位）是否一致


================================================================
  十一、上下文保护：CC#2存在的意义
================================================================

  为什么CC#2必须是一个独立会话
  ---------------------------------
  CC#1（中枢大脑）的上下文窗口是最稀缺的资源。就像一个
  总指挥不能亲自去搬砖——搬砖消耗的体力会让他在关键时刻
  做不出正确决策。

  CC#1的上下文预算（理想状态）：
  ├ 项目框架 + 决策记录    ~30%
  ├ 当前阶段关键信息        ~20%
  └ 留给思考和判断          ~50% ← 这个空间决定决策质量

  如果CC#1没有CC#2，自己去读代码、跑程序、看日志：
  ├ 完整代码                ~40%  ← 噪声
  ├ 运行日志 + 数据         ~30%  ← 噪声
  ├ 调试过程                ~20%  ← 噪声
  └ 留给思考和判断          ~10%  ← 太少了！决策质量崩溃

  CC#2把上面所有"噪声"吞掉，只把精简结论（"通过了/没通过/
  卡在哪了"）喂给CC#1。CC#1保留50%的思考空间。

  任务分流规则
  ---------------------------------
  ┌──────────────────────────┬─────────────────────┐
  │         任务类型         │       谁来做        │
  ├──────────────────────────┼─────────────────────┤
  │ 代码编写（≤300行）       │ CC#2               │
  │ 代码编写（>300行/高难度）│ 外部模型→CC#2整合  │
  │ 代码运行 + 测试          │ CC#2               │
  │ 运行日志阅读 + 提炼      │ CC#2 → 精简汇报    │
  │ PDF/图片数据提取          │ 外部模型(Flash)    │
  │ 算法逻辑审查             │ 外部模型(Pro)+CC#1 │
  │ 论文审阅                 │ 外部模型(Pro)      │
  │ 数据格式转换             │ CC#2               │
  │ 图表生成                 │ CC#2               │
  │ 最终决策 + 项目方向      │ CC#1（不可委托）   │
  └──────────────────────────┴─────────────────────┘

  CC#1上下文污染的告警信号
  ---------------------------------
  以下任一信号出现，说明你的CC#1已经被噪声污染，
  必须立即把正在做的事分流给CC#2：

  ⚠️ 信号1：你在逐行阅读代码
      → 应该：只审控制流（"这段逻辑对不对"）
      → 不应该：逐行理解每个变量（"这个i为什么从1开始"）

  ⚠️ 信号2：你在手动调整数据格式
      → 应该：告诉CC#2"按XX格式输出"
      → 不应该：自己改CSV里的逗号和空格

  ⚠️ 信号3：你在反复运行同一个命令调试
      → 应该：把调试任务整个丢给CC#2
      → 不应该：在CC#1会话里用bash反复试

  记住一句话判断标准：
  "你现在做的是在验证控制流和设计契约，还是在做语法纠错
   和手动格式对齐？前者是CC#1该做的，后者是CC#2该做的。"


================================================================
  十四、降级方案：资源不够怎么办
================================================================

  场景1：我只有1个外部模型（比如只有Gemini网页版）
  ---------------------------------
  使用"会话级降级"：

  1. 浏览器开新Tab #1（无历史）
     粘贴角色锁定词 + 待审内容
     获得第1轮审查意见 → 保存

  2. 关闭Tab #1
     重新开新Tab #2（确保全新的上下文）
     粘贴角色锁定词 + 同样的待审内容
     获得第2轮审查意见 → 保存

  3. CC#1对比两轮意见
     注意：两轮都用同一个模型，审查质量不如标准级。
     但通过清零上下文和角色锁定，模拟了"两个独立审查者"。
     标注 [会话级审查]。

  场景2：我没有任何外部模型（只有Claude Code本身）
  ---------------------------------
  使用"单点级应急降级"：

  1. CC#1审查（从项目约束和设计逻辑角度）
  2. CC#2审查（从代码实现和运行结果角度）
  3. 两人独立审查后交换意见
  4. 终审时标注 [单模型审查·风险自担]

  注意：单点级的可靠性最低。如果是竞赛/学术等高风险场景，
  尽量创造条件获得至少1个外部模型。

  场景3：CC#2掉线了（会话断开或API出问题）
  ---------------------------------
  1. 在CC#1的上下文中，记录CC#2已经完成的产出物
  2. 重新启动CC#2会话
  3. 使用"交接快照"恢复上下文
  4. CC#2确认理解后，从中断点继续


================================================================
  十五、外部模型群：5类工具怎么用
================================================================

  类型1：算法生成者
  ---------------------------------
  什么时候用：遇到高难度算法（回溯、DP、多目标优化等），
  CC#2写起来吃力或容易出错。

  怎么用：
  1. CC#1把算法需求提炼为清晰的文字描述（不是代码）
  2. 你复制需求，粘贴给外部模型（GPT 5.5 / Gemini 3.1 Pro）
  3. 外部模型返回伪代码或完整代码
  4. 你把代码交给CC#2整合到项目中
  5. CC#2测试后汇报结果

  竞赛场景特别注意：只参考算法思路，独立重写，不直接复制代码。

  类型2：代码审查者
  ---------------------------------
  什么时候用：CC#2完成了核心代码，需要独立视角发现逻辑漏洞。

  怎么用：
  1. CC#1说"准备交接给外部审查"
  2. CC#2生成 handoff_payload.txt
  3. 你复制到新Tab，粘贴给外部模型
  4. 外部模型返回：问题列表 + 行号 + 修改建议
  5. 你把意见带回CC#1
  6. CC#1综合 → 裁决 → 下达给CC#2修改

  类型3：论文审阅者
  ---------------------------------
  什么时候用：论文初稿或终稿完成后，定档前。

  怎么用：
  1. 把论文正文 + 关键图表粘贴给外部模型
  2. 附上审查要求："请从逻辑漏洞、论证缺陷、格式问题、
     数据一致性四个维度独立审查"
  3. 外部模型返回意见
  4. CC#1综合 → 裁决 → CC#2执行修改

  类型4：文件提取者
  ---------------------------------
  什么时候用：赛题PDF、图片数据、Word中的表格等Claude Code
  无法直接读取的文件。

  怎么用：
  1. 上传文件到网页端AI（Gemini Flash等轻量模型即可）
  2. "请将表格完整提取为Python dict格式，变量名用XXX"
  3. 拿到输出后，交给CC#1验证数据完整性
  4. 验证通过后保存为data.py

  类型5：需求提炼者
  ---------------------------------
  什么时候用：项目刚开始时，需求很模糊，不知道从哪拆起。

  怎么用：
  1. 把你脑子里模糊的想法全部倒给外部模型
  2. "请将这些需求整理为结构化的项目阶段文档"
  3. 拿到结构化需求后，交给CC#1审核和细化
  4. CC#1基于此制定正式的项目阶段计划


================================================================
  十六、常见问题与排查
================================================================

  Q1：阀门卡住了怎么办（修改了3轮还是不过）？
  ---------------------------------
  可能原因：
  - 验收标准定得太严（要求和工具能力不匹配）
  - 需求本身有问题（需要重新评估阶段目标）
  - CC#2对需求的理解有偏差（需要重新对齐，不是重审）

  解决：
  - 暂停执行，CC#1重新评估验收标准
  - 如果标准合理但CC#2确实做不到 → 考虑降级为"部分通过，
    剩余留到下阶段补"或换外部模型接手
  - 如果标准太高 → 调整标准，重新开阀门

  Q2：为什么不能跳过交叉审查？
  ---------------------------------
  因为单AI的盲区是系统性的。本次C题中，多个关键漏洞都是
  外部模型发现的——如果跳过，论文交上去就直接扣分。

  如果你真的没有外部模型（单点级），也必须CI#1+CC#2独立
  审查并标注风险。阀门可以降级，但绝不能跳过。

  Q3：CC#1和CC#2可以用同一个模型吗？
  ---------------------------------
  可以。关键是"独立会话"不是"不同模型"。CC#1和CC#2的
  物理隔离（两个独立窗口）本身就是最核心的保护机制。

  但外部交叉审查时，最好使用与CC#1不同的模型——不同模型
  的推理路径不同，盲区互补效果更好。

  Q4：复制粘贴太多了，能自动化吗？
  ---------------------------------
  当前版本的自动化程度有限。但以下操作已经帮你省了大量体力：
  - CC#2自动生成 handoff_payload.txt（不需要你手动拼接）
  - B级和C级审查全部在本地闭环（不需要复制到外部）
  - 只有A级和重大交叉审查才需要复制到网页端

  v3.0计划引入半自动编排代理，目标是消除所有人工复制粘贴。

  Q5：项目进行到一半发现阶段拆分不合理怎么办？
  ---------------------------------
  可以调整。但必须：
  1. 当前阶段先关阀门（确认已完成的不会白做）
  2. CC#1重新拆解剩余阶段
  3. 与CC#2同步新的阶段计划
  4. 继续执行

  不要在阶段中临时改计划——那会导致阀门失去意义。

  Q6：外部模型意见和我自己的判断冲突怎么办？
  ---------------------------------
  这是正常情况。外部模型没有你的完整项目上下文，
  他们可能提出技术上正确但项目上不合适的建议。

  CC#1有权驳回外部意见，但驳回必须：
  1. 写明理由（不是"我觉得不对"，而是"因为X约束，所以Y建议不适用"）
  2. 记录在决策日志中
  3. 如果是两个外部模型都指出的问题 → 驳回之前要非常慎重

  Q7：我能跳过某个阶段直接做后面的吗？
  ---------------------------------
  不能。阶段的顺序不是装饰——每个阶段的输出是下一阶段的输入。
  跳阶段等于拿着没有验证的数据往下做，错误会累积。
  一个例外：独立子任务可以并行（如代码开发和论文撰写同时进行），
  但它们的阀门必须各自独立通过。


================================================================
  十七、实际开发中可能遇到的问题汇总
================================================================

  以下问题均来自C题项目实战中真实遇到的痛点，以及工作流
  设计过程中预判的潜在风险。

  问题1：CC#1上下文被噪声污染
  ---------------------------------
  表现：CC#1开始逐行读代码、手动调格式、反复执行同一命令。
  根因：CC#1没有把执行任务分流给CC#2。
  解决：触发模块8的L2告警→立即分流。如果已经严重退化，
    执行L3检查点切换：写检查点→新会话→恢复。

  问题2：第二天开机后不知道从哪里开始
  ---------------------------------
  表现：新会话中CC#1完全不记得项目状态，需要花10分钟重建上下文。
  根因：DeepSeek/VSCode无持久记忆，前一天没有保存检查点。
  解决：严格执行关机协议。每天结束前CC#1更新项目状态_当前.md。
    第二天新会话粘贴"恢复项目。读取 项目状态_当前.md。"。

  问题3：高偏好项在结果中无声消失
  ---------------------------------
  表现：A2(喜好度9.2最高)在最优方案中完全缺席，但代码没有报错。
  根因：约束过于严格导致可行域收缩，但代码逻辑本身没有bug。
  解决：模块6的静默bug检测——偏好-入选一致性检查。
    运行后自动验证：高偏好景点是否至少在某个可行方案中出现。
    若不在→分析是约束过严还是真的不可行。

  问题4：枚举算法性能爆炸
  ---------------------------------
  表现：v1全排列跑了5小时，53M方案几乎全被过滤。
  根因：约束放宽后缓存过滤率骤降，全排列架构承受不了。
  解决：模块9的高难度判定+伪代码预审。
    复杂度预估≥O(N·M)且N≥1000时→先审伪代码→脑补极端case→
    确认架构可行后再写完整代码。枚举类直接上回溯，不走全排列弯路。

  问题5：阶段间数据不同步
  ---------------------------------
  表现：stage2改了方案，stage3的硬编码数据还是旧的。
  根因：跨阶段数据通过人工复制传递，没有结构化文件。
  解决：模块2的JSON/CSV数据契约。输出方写文件，下游读文件。
    stage3不再硬编码PLAN数据，改为读取stage2输出的solution.json。

  问题6：全天项目跑着跑着CC#1开始绕圈子
  ---------------------------------
  表现：决策质量下降、废话增多、反复问同一个问题。
  根因：上下文老化（信息密度过高·噪声>信号）。
  解决：L2告警触发→当前决策完成后→L3检查点切换→新会话。
    预防：L1分流让CC#2吞掉噪声。CC#1永远不看>50行代码。

  问题7：外部模型审查时"偷懒"
  ---------------------------------
  表现：外部AI回复"代码看起来没问题"但没有给出具体分析。
  根因：复用了旧Tab，外部AI受历史上下文影响产生自证幻觉。
  解决：模块9的Tab硬隔离。每次审查必须新开浏览器Tab（无历史）。
    首句角色锁死："你是冷酷的静态审计员。唯一职责是找Bug。"

  问题8：用户手动修改了AI的代码
  ---------------------------------
  表现：用户在传递过程中觉得"这里改一下更好"，自己动手改了。
    导致CC#2不知道代码已经被改过，后续修改基于错误状态。
  根因：用户没有遵守只读中继协议。
  解决：铁律——你只做复制粘贴。想改代码？告诉CC#2去改。
    如果发现代码有问题，把这句原话发给CC#2："修改XX文件的YY行"。

  问题9：论文/文档在多人审查后不知道怎么改
  ---------------------------------
  表现：Gemini Pro给了5条意见，GPT给了3条意见，其中2条互相矛盾。
  根因：没有CC#1做综合裁决。
  解决：模块7的CC#1综合流程。一致指出→必改。分歧→追问深挖→
    CC#1拍板。只有一方指出→CC#1研判。最终决策记录：
    "采纳了X·驳回了Y·理由是Z"。

  问题10：阶段回溯后代码和AI状态不同步
  ---------------------------------
  表现：CC#1读旧检查点回到阶段1，但CC#2的代码还在阶段3。
  根因：只回溯了大脑，没有回溯代码。
  解决：原子回溯指令——必须同时执行：①CC#1读旧MD ②CC#2 git
    checkout stage-X-pass ③CC#2运行环境检查确认数据匹配。

================================================================
  十二、检查点系统（v2.1新增）
================================================================

  为什么需要这套机制
  ---------------------------------
  DeepSeek/v4pro没有持久记忆，VSCode终端关闭后会话消失。
  磁盘是唯一可靠的存储。这套机制让工作流不依赖任何AI的记忆。

  核心文件
  ---------------------------------
  项目状态_当前.md → 存项目根目录。任何时候打开就是当前状态。
  .workflow_history/ → 历史阀门快照（StageX_日期.md）

  日常关机（5分钟）
  ---------------------------------
  1. CC#1更新 项目状态_当前.md（确认所有字段最新）
  2. 保存到项目目录
  3. 第二天新会话：
     CC#1 → "恢复项目。读取 项目状态_当前.md。"
     CC#2 → "恢复项目。读取 [CC#2恢复用部分]。"
  4. 双方确认 → 继续

  CC#1上下文满了（告警信号）
  ---------------------------------
  任一信号→准备切换：
  - 对话已跨越2个以上阶段阀门
  - CC#1开始频繁回看之前内容
  - 回答质量下降（废话变多、绕圈子）

  切换规则：
  - 必须等当前决策完成后（禁止在讨论/裁决中途切）
  - 写入检查点 → 开新CC#1 → 恢复 → 验证 → 关闭旧会话

  CC#2上下文满了
  ---------------------------------
  告警信号：输出不再精简(倾倒日志)/反复修改同一个地方/说"需要重新了解项目"
  切换：不需等决策。存盘→更新检查点→新会话→恢复→汇报

  阶段回溯（发现方向错了）
  ---------------------------------
  回溯到任意历史阀门出口：
  1. CC#1读取 .workflow_history/StageX_日期.md
  2. CC#2执行 git checkout stage-X-pass
  3. CC#2运行环境检查 → 确认代码/数据匹配
  ⚠️ 仅锚定阀门点，不支持中途回溯。

  崩溃恢复（电脑蓝屏/VSCode崩了）
  ---------------------------------
  全部丢失 → 项目状态_当前.md 是最后防线
  CC#2代码从最后一次 git commit 恢复

  维护责任
  ---------------------------------
  检查点文件由CC#1（AI）自动输出，用户只负责Ctrl+C/V保存。
  CC#2每次产出后立即存盘。
