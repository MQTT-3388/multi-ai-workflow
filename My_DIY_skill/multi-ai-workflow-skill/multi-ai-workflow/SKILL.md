# 多AI协作工作流 v2.1 — 星型中枢架构

## 设计原理

本工作流基于**控制论星型中枢模型**：CC#1作为决策中枢，CC#2作为本地执行代理吞噬噪声，外部模型群作为异构探针提供多视角验证。核心目标是**用计算开销换取决策中枢上下文纯净度**——CC#2吞掉所有代码细节、运行日志、调试噪声，只将精简信号呈报CC#1；外部模型群从不同角度独立审视产出，弥补单一AI的系统性盲区。

## 架构总览

```
              ┌──────────────────────┐
              │   CC#1（中枢大脑）     │
              │  推进·审核·决策·拍板   │
              └────┬─────────┬───────┘
                   │         │
      ┌────────────┘         └────────────┐
      ▼                                   ▼
┌─────────────┐                 ┌──────────────────┐
│ CC#2（副手） │                 │  外部模型群       │
│ 执行·同步   │                 │ 算法生成·代码审查  │
│ 吞噬噪声    │                 │ 论文审阅·文件提取  │
│ 保护CC#1   │                 │ 多视角独立验证     │
└─────────────┘                 └──────────────────┘
```

## 快速启动

用户说"启动多AI工作流"后：

### 0. 项目初探（新增）
```
1. [brainstorming] 澄清需求、探索方案、输出设计文档
   → 硬性门禁：设计未批准，禁止任何实现动作
2. [using-superpowers] 扫描可用工具集
3. 用户批准设计 → 进入步骤1
```
输出：需求摘要 + 设计文档 + 可用工具清单

### 1. 确认模式
```
mode: "hybrid"（默认，本地API+网页端）| "api_full"（全API）
```
纯网页端或无API时自动降级。

### 2. 定义角色
```
CC#1（中枢）：推进项目、审核产出、综合各方意见、最终拍板。不写代码。
CC#2（副手）：承接执行任务、运行测试、生成图表。存在意义是保护CC#1上下文。
外部模型群：按需调用5类工具（算法生成/代码审查/论文审阅/文件提取/需求提炼）。
用户（协调者）：AI间信息传递、最终确认交付。必须保持"只读中继"——不手动修改AI产出。
```

### 3. 拆解阶段
将项目拆为3~7个阶段，每阶段定义：输入/输出/验收标准/由谁审查。

### 4. 执行循环
```
CC#1分发任务 → CC#2执行 → CC#2精简汇报 → CC#1审查 → 通过/修改
重大结果 → 强制外部交叉审查（≥2轮独立分析） → CC#1综合拍板 → 定档
阶段结束 → 阀门（通过→下阶段 | 修改→重审≤3轮 | 驳回→重做）
```

### 5. 终审与归档
全部阶段通过 → 全局硬约束核验 + 静默bug检测 → 6类目录归档

## 核心模块

### 模块1：角色定义

| 角色 | 职责 | 禁止 |
|------|------|------|
| CC#1（中枢） | 推进节奏、审核产出、驱动外部对话、综合决策、最终拍板 | 阅读完整代码、逐行调试、手动格式化数据 |
| CC#2（副手） | 承接CC#1任务、写代码/运行/出图、精简汇报、持续同步 | 自行裁决模型局限性、倾倒原始输出给CC#1 |
| 外部模型群 | 算法生成、代码审查、论文审阅、文件提取、需求提炼 | 直接修改项目文件、跳过CC#1自行决策 |
| 用户（协调者） | AI间信息传递、启动/确认流程、最终交付 | 手动修改AI产出代码、在传递中夹带自己解读 |

### 模块2：阶段规划
将项目拆为3~7个阶段。每阶段必须定义：输入文件、输出文件、验收标准、审查者。跨阶段数据必须通过结构化文件（JSON/CSV）传递，禁止硬编码。

**硬性前置**：阶段0或阶段1必须执行 `git init`（阶段回溯机制依赖git tag，无git环境则回溯瘫痪）。

### 模块3：审查分级

| 级别 | 适用 | 做什么 | 耗时 |
|------|------|--------|------|
| A级 | 核心算法/关键约束 | 控制流验证+边界推演+契约审计 | 30-60min |
| B级 | 可视化/格式 | 抽查逻辑+输出格式 | 10-20min |
| C级 | 调参重跑 | 约束清单核对 | 5-10min |
| D级 | 跨模型交叉 | 外部AI独立审查（算法/论文/数据） | 按需 |

### 模块4：阶段阀门
```
通过 → 下一阶段 | 需修改 → 重审(最多3轮) | 驳回 → 重做
```
重大结果定档前，必须先完成强制交叉审查（模块7）。交叉审查未完成，阀门不可打开。

### 模块5：同步加固与检查点系统

**核心机制**：`项目状态_当前.md` — 存项目根目录。磁盘上唯一的真相源。任何AI会话都能读。任何时候打开就是当前状态。

**检查点文件结构**：
```markdown
# 项目状态 — [项目名] — Stage X
## 骨架（始终保留）
- 项目目标/阶段清单/角色配置
## 当前状态（阀门通过后更新）
- 当前阶段/已通过阶段/待裁决/下一步
## 决策记录（只记结果）
## 数据契约（防失忆核心）- 变量名/格式/单位/索引
## CC#2恢复用 - 上次产出/当前任务/已修改文件/阻塞/关键路径
## 外部模型状态 - 上次审查结论/待审查产出
```

**写入时机与规则**：

| 触发 | 操作 |
|------|------|
| 阶段阀门通过 | CC#1**必须自动输出**完整的检查点文本，提醒用户保存。保存前将旧文件备份到 `.workflow_history/StageX_日期.md` |
| 每天关机前 | CC#1主动更新检查点，确认所有字段最新 |
| CC#1上下文老化（准备换会话） | 在安全切换点写入检查点 |
| CC#2上下文老化（自己切换） | 在检查点的"CC#2恢复用"字段更新当前状态 |

**硬性指令**：检查点文件的维护责任由CC#1（AI）承担。阀门通过后CC#1必须输出更新后的完整文本。

**用户保存前强制Review**：保存检查点文件前，用户必须花10秒人眼确认：①"当前阶段"是否正确 ②"数据契约"中的变量名/格式/单位是否被AI篡改。CC#1生成状态时可能产生幻觉（如误写阶段号），人眼10秒即可拦截。

根目录只保留 `项目状态_当前.md`，历史快照存 `.workflow_history/`。

**CC#2汇报规范**：
```
【CC#2 → CC#1 阶段X汇报】
完成：[做了什么]  结果：[关键数据摘要]
问题：[需CC#1决策]  原始输出：[保留在CC#2会话]
```
原则：只呈报信号，不倾倒噪声。

**交接快照**（CC#1→外部模型）：
```markdown
【网页端审查冷启动快照 v2.0】
1. 阶段上下文  2. 数据契约  3. 审查任务  --- [待审内容+运行日志]
```
CC#2自动生成 `handoff_payload.txt`，用户一键复制。

**防御性断言**：下游代码入口必须包含Assert Guards。

**跨阶段数据契约**：输出方提供JSON/CSV，下游读文件不硬编码。

**版本控制与阶段回溯**：

| 规则 | 操作 |
|------|------|
| 代码打标 | CC#2每次阀门通过时：`git tag stage-X-pass` |
| CC#2每次产出后 | 立即保存到磁盘。每完成可运行小功能：`git commit -m "wip: [简述]"` |
| 原子回溯指令 | 回溯时必须同时：①CC#1读取 `.workflow_history/StageX.md` ②CC#2执行 `git checkout stage-X-pass` ③CC#2运行环境检查确认代码/数据匹配 |
| 回溯定位 | 灾难恢复工具，非日常导航。不锚定在非阀门点 |

**关机/上下文切换协议**：
- 关机前5分钟：CC#1更新检查点 → 确认保存
- 第二天/新会话："恢复项目。读取 项目状态_当前.md。"（CC#1和CC#2各自粘贴对应部分）
- CC#1切换时机：当前决策完成后（禁止在讨论中途切换）
- CC#2切换：不需等决策。告警触发→存盘→新会话→汇报

### 模块6：项目终审
所有阶段阀门通过后：全局硬约束逐条核验 → 静默bug检测（偏好-入选一致性、缓存覆盖率、约束边界贴近度）→ 交付物清单核对 → 上下游数据一致性。

### 模块7：强制交叉审查（硬性规则）

**规则**：任何重大任务结果在定档前，CC#1必须获取至少2轮独立审查意见。

"重大任务结果"包括：数学模型、核心算法结果、论文初稿/终稿、交付下游的数据文件。

**审查层级**（按资源可用性自动降级）：

| 层级 | 条件 | 操作 |
|------|------|------|
| 标准级 | ≥2个异构模型可用 | 模型A独立审查 + 模型B独立审查，CC#1对比综合 |
| 会话级 | 仅1个模型可用 | 同一模型，新Tab+清空上下文+Temp=0+角色锁定，执行2轮独立审查 |
| 单点级 | 0个外部模型 | CC#1+CC#2自审，终审时标注`[单模型审查·风险自担]` |

**CC#1的拍板权与约束**：
- 有权：最终决定采纳/驳回任何意见（驳回需有理由）
- 必须：收到≥2轮独立审查后才能拍板 | 分歧时追问双方深挖，不可跳过 | 决策记录："采纳了X，驳回了Y，理由是Z"

### 模块8：上下文保护（四层防御体系）

CC#1的上下文是项目最稀缺资源。CC#2存在的首要目的是**保护它不被污染**。

**L1·CC#2分流（预防）**：
| 任务 | 谁做 |
|------|------|
| 代码编写+运行+测试 | CC#2 |
| 高难度算法(>300行) | 外部模型→CC#2整合 |
| 运行结果提炼 | CC#2→精简汇报 |
| PDF/图片提取 | 外部模型(Flash) |
| 算法逻辑审查 | 外部模型(Pro) + CC#1 |
| 论文审阅 | 外部模型(Pro) |
| 最终决策+框架推进 | CC#1（不可委托） |

**L2·告警信号（发现污染）**：

| CC#1信号 | CC#2信号 |
|----------|---------|
| 在逐行读代码（非控制流验证） | 输出不再精简，开始倾倒原始日志 |
| 在手动调格式（非审设计逻辑） | 反复修改同一个地方 |
| 回答质量下降（废话变多·绕圈子） | 收到新任务时说"需要重新了解项目" |
| 对话已跨越2个以上阀门 | — |

出现任一信号→立即分流（CC#1）或自我切换（CC#2）。

**L3·检查点切换（修复）**：
- CC#1：当前决策完成→写入检查点→新会话→恢复→验证→关闭旧会话。禁止在讨论/裁决中途切换
- CC#2：不需等决策。存盘→更新检查点→新会话→恢复→汇报

**L4·磁盘快照（兜底）**：
关机/崩溃/断电→从 `项目状态_当前.md` 冷恢复。最坏情况回退到上一个阀门出口。

### 模块9：用户中继协议

用户在混合模式下是AI间的数据桥梁。必须遵守：

1. **只读中继**：禁止手动修改任何AI产出的代码/文本。如需修改，发给CC#2执行。
2. **无损传递**：原样复制粘贴，不添加自己的解读或暗示。
3. **一键交接**：使用CC#2生成的 `handoff_payload.txt`，Ctrl+A一键复制到网页端，消灭碎片化粘贴。
4. **网页端Tab硬隔离**：每次外部审查必须新建浏览器Tab（无历史上下文），首句使用角色锁定词："你现在是冷酷的静态审计员。唯一职责是寻找Bug和逻辑漏洞。禁止输出可运行代码。请确认职责。"

## 外部模型群（5类按需调用）

| 类型 | 用途 | 建议模型 |
|------|------|---------|
| 算法生成者 | 高难度算法编写、伪代码设计 | GPT 5.5 / Gemini 3.1 Pro |
| 代码审查者 | 独立审查CC#2的代码逻辑 | Gemini 3.1 Pro / Claude Opus |
| 论文审阅者 | 审阅论文初稿、发现逻辑漏洞 | Gemini 3.1 Pro |
| 文件提取者 | PDF/图片等CC无法直接读取的数据 | Gemini 3.1 Flash |
| 需求提炼者 | 模糊需求→结构化文档 | Gemini 3.1 Flash / CC#1自带 |

CC#1主动驱动与外部模型的对话（提问→追问→对比→综合），外部模型之间不直接通信。

## 任务路由决策

CC#1判断任务归属：
```
是否需要写代码？
├ 是 → 高难度算法？(判定标准见下)
│      ├ 是 → [web-access] 搜GitHub/论文 → 提取思路/高质量代码
│      │       ├ 竞赛模式：只提取算法思路+伪代码 → 独立重写
│      │       └ 非竞赛模式：评估代码质量 → 高质量直接复用/低质量退化为思路提取
│      │       ↓
│      │      外部模型生成 → CC#2整合 → 多AI交叉审查
│      │
│      └ 否 → ≤300行？ → CC#2直接写
│             >300行？ → 外部模型生成→CC#2整合
│
├ 需要审查？ → 外部模型独立审 → CC#1综合
├ 需要提取文件？ → 外部模型(Flash)
└ 需要最终决策？ → 只有CC#1
```

高难度判定（满足任一）：
- 递归/回溯/DP/图论 | 约束≥3个或目标≥2个 | 复杂度≥O(N·M)且N≥1000 | 需外部求解器

## 适用性判断

**适合**（全部满足）：角色可分(CC#1+CC#2+≥1外部模型) | 标准可量化 | 时间≥4h

**不适合**：单人单AI | 实时调试 | 高度探索性 | 需求剧烈变动 | 单文件<200行

## 与其他Skill联动（Superpowers技能包）

本工作流深度集成 [superpowers](https://github.com/anthropics/superpowers) 技能包。

### 深度集成（改变工作流结构）

| Skill | 集成位置 | 作用 |
|-------|---------|------|
| `brainstorming` | **阶段0：项目初探** | 硬性门禁：设计未批准禁止实现。输出设计文档→自动衔接writing-plans |
| `verification-before-completion` | **模块4：阶段阀门** | 阀门的执行引擎。"无新鲜验证证据，不准声明完成" |
| `using-superpowers` | **会话启动** | 建立优先级：用户指令(CC#1角色定义) > superpowers > 系统默认 |

### 中度集成（增强现有模块）

| Skill | 增强哪个模块 | 效果 |
|-------|------------|------|
| `writing-plans` | 模块2 阶段规划 | brainstorming完成后自动衔接，生成正式执行计划 |
| `executing-plans` | CC#2执行 | CC#2按计划逐项执行，不偏离 |
| `requesting-code-review` | 模块3 A/B级审查 | 标准化审查请求格式+审查者prompt模板 |
| `systematic-debugging` | 模块7 审查发现bug后 | 根因追溯替代猜测式修复 |
| `subagent-driven-development` | 模块8 CC#2任务分流 | CC#2内部并行处理独立子任务 |

### 轻度集成（便利工具）

| Skill | 场景 |
|-------|------|
| `doc-coauthoring` | 论文/文档撰写阶段，结构化协作文档 |
| `dispatching-parallel-agents` | CC#1层面分发无依赖并行任务 |
| `web-access` | **模块10：外部代码搜索**。高难度算法触发，GitHub/论文搜索，竞赛模式(思路提取+独立重写)/非竞赛模式(质量评估+复用或重写) |
| `docx` / `pdf` / `xlsx` | 文档/数据/图表生成 |
| `test-driven-development` | 项目要求TDD时启用 |
| `receiving-code-review` | CC#2收到审查反馈后的规范处理 |
| `webapp-testing` | CC#2 Web应用测试（可选，涉及前端时启用） |
| `security-review` | 终审前安全审查（可选，安全敏感项目启用） |
| `init` | 项目启动后自动生成项目文档（可选） |

### 无冲突确认

全部superpowers skill与本工作流互补，触发时机互不重叠。`verification-before-completion`作为阀门执行引擎，`brainstorming`作为阶段0入口。
