## 一、设计原理

### 1.1 控制论星型中枢模型

本工作流基于控制论负反馈架构：

```
输入(需求) → CC#1(决策中枢) → 执行(CC#2) → 产出 → 审查(外部模型群) → 反馈 → CC#1修正 → 收敛
```

对比传统线性瀑布模型（状态流转脆弱，一环出错全线回溯），星型中枢通过多探针负反馈实现快速状态收敛。

### 1.2 信息熵控制

CC#1的上下文窗口是项目最稀缺资源。核心设计原则：**用计算开销（CC#2+外部模型群）换取决策中枢上下文纯净度**。CC#2吞掉所有代码细节、运行日志、调试噪声（信息熵高），仅将精简信号呈报CC#1（信息熵低）。

详见模块8。

## 三、12个模块详规

### 模块1：角色定义

| 角色 | 职责 | 禁止 |
|------|------|------|
| CC#1（中枢） | 推进节奏、审核产出、**主动驱动外部对话**、综合决策、最终拍板 | 阅读完整代码(>50行)、逐行调试、手动格式化数据 |
| CC#2（副手） | 承接CC#1任务、写代码/运行/出图、**精简汇报**、持续同步。**存在意义：保护CC#1上下文** | 自行裁决模型局限性、倾倒原始输出给CC#1 |
| 外部模型群 | 5类按需调用（下文详述）。CC#1主动驱动，多视角独立验证 | 直接修改项目文件、跳过CC#1自行决策、外部模型之间直接通信 |
| 用户（协调者） | AI间信息传递、启动/确认流程、最终交付。**必须只读中继** | 手动修改AI产出代码、在传递中夹带自己解读 |

### 模块2：阶段规划
项目拆为3~7个阶段。每阶段定义：输入/输出/验收标准/审查者。跨阶段JSON/CSV传递不硬编码。独立子任务可并行。**硬性前置：阶段0/1必须 `git init`。**

### 模块3：审查分级

| 级别 | 适用 | 审查内容 | 时间 |
|------|------|---------|------|
| A级 | 核心算法/关键约束 | 控制流验证+边界推演+契约审计 | 30-60min |
| B级 | 可视化/格式转换 | 抽查逻辑+输出格式+数据一致性 | 10-20min |
| C级 | 调参重跑/小修 | 约束清单+数值合理性 | 5-10min |
| D级 | 跨模型交叉 | 外部AI独立审查（算法/论文/数据） | 按需 |

**审查者模型不能与代码生成者相同。**

### 模块4：阶段阀门
```
通过 → 下一阶段 | 需修改 → 重审(≤3轮) | 驳回 → 重做
```
重大结果定档前必须先完成模块7的强制交叉审查。未完成→阀门不可打开。

### 模块5：同步加固与检查点系统

**核心机制**：`项目状态_当前.md` — 磁盘上唯一真相源。AI会话可随时替换，从文件恢复。

**检查点结构**：骨架(项目目标/阶段清单/角色配置) + 当前状态(阶段/待裁决/下一步) + 决策记录 + 数据契约(防失忆核心) + CC#2恢复用字段 + 外部模型状态。

**写入触发**：阀门通过(CC#1自动输出，旧文件备份到 `.workflow_history/StageX_日期.md`) | 关机前手动确认 | CC#1/CC#2上下文老化切换。

**CC#2汇报规范**：精简格式[完成/结果/问题]，原则"只呈报信号，不倾倒噪声"。

**交接快照**：CC#2自动生成handoff_payload.txt（快照+代码+日志），用户一键复制到网页端。

**防御性断言 + JSON数据契约**：下游代码入口Assert Guards，跨阶段JSON/CSV传递不硬编码。

**阶段回溯**：代码 `git tag stage-X-pass` + 检查点 `.workflow_history/`。原子指令：CC#1读旧MD + CC#2 git checkout + 环境检查。仅锚定阀门点，灾难恢复工具。

### 模块6：项目终审
全局硬约束逐条核验 → 静默bug检测（偏好-入选一致性、缓存覆盖率、约束边界贴近度）→ 交付物清单 → 上下游数据一致性 → 跨模块逻辑闭环。

### 模块7：强制交叉审查 ⭐

**规则**：任何重大结果定档前，CC#1必须获取≥2轮独立审查意见。

"重大结果"：数学模型、核心算法结果、论文初稿/终稿、交付下游的数据、终审前全部交付物。

**审查层级（自动降级）**：

| 层级 | 条件 | 操作 |
|------|------|------|
| 标准级 | ≥2个异构模型 | 模型A审+模型B审，独立交叉，CC#1对比综合 |
| 会话级 | 仅1个模型 | 新Tab+清空上下文+Temp=0+角色锁定，2轮独立审查 |
| 单点级 | 0个外部模型 | CC#1+CC#2自审，标注`[单模型审查·风险自担]` |

**CC#1拍板权与约束**：
- 有权：最终决定采纳/驳回（驳回需理由）
- 必须：收到≥2轮独立审查后才能拍板 | 分歧时追问双方深挖 | 记录"采纳X、驳回Y、理由Z"

**为什么是硬性规则**：单AI盲区是系统性的。C题中Gemini Pro发现了CC#1未发现的"半日游"漏洞，A2排除是CC#2分析缓存发现。多模型交叉才能逼近全覆盖。

### 模块8：上下文保护（四层防御体系）

CC#2存在的首要目的：保护CC#1上下文。

**L1·CC#2分流（预防）**：分流规则表同上。核心：CC#2吞噪声，CC#1看信号。

**L2·告警信号（发现）**：CC#1信号(逐行读代码/手动调格式/回答退化/跨2阀门) | CC#2信号(倾倒日志/反复修改/失忆)。任一→立即分流或自我切换。

**L3·检查点切换（修复）**：CC#1在安全决策点切换，CC#2不需等决策。写入检查点→新会话→恢复。

**L4·磁盘快照（兜底）**：关机/崩溃→从 `项目状态_当前.md` 冷恢复。最坏回退到上一阀门出口。

**CC#1上下文告警原则**：
当发现自己"语法级纠错、逐行翻译或手动格式对齐"（而非"控制流验证、边界推演或契约审计"）时，上下文已被污染，立即分流给CC#2。

### 模块9：用户中继协议

混合模式下用户是AI间数据桥梁。必须遵守：

1. **只读中继**：不手动修改任何AI产出。需修改→CC#2执行。
2. **无损传递**：原样复制粘贴，不加解读或暗示。
3. **一键交接**：使用CC#2生成的handoff_payload.txt。
4. **Tab硬隔离**：每次外部审查新建浏览器Tab（无历史），首句角色锁定。

### 模块10：外部模型群

5类按需调用（非全部必须）：

| 类型 | 用途 | 建议模型 |
|------|------|---------|
| 算法生成者 | 高难度算法/伪代码 | GPT 5.5 / Gemini 3.1 Pro |
| 代码审查者 | 独立审查代码逻辑 | Gemini 3.1 Pro / Claude Opus |
| 论文审阅者 | 审论文漏洞+格式 | Gemini 3.1 Pro |
| 文件提取者 | PDF/图片→数据 | Gemini 3.1 Flash |
| 需求提炼者 | 模糊需求→结构化文档 | Gemini 3.1 Flash / CC#1自带 |

CC#1主动驱动对话（提问→追问→对比→综合），外部模型间不直接通信。

### 模块11：任务路由

CC#1判断任务归属：
- 写代码≤300行&非高难度→CC#2
- 写代码>300行或高难度→外部模型生成→CC#2整合
- 需审查→外部模型独立审→CC#1综合
- 需提取文件→外部模型(Flash)
- 最终决策→只有CC#1

高难度判定（满足任一）：递归/回溯/DP/图论 | 约束≥3或目标≥2 | 预估≥O(N·M)且N≥1000 | 需外部求解器

### 模块12：归档标准

6类目录：01核心产出/02提交材料/03AI协作记录/04参考材料/05工具脚本/06论文备忘。原文件不移动，无临时文件，无身份信息，复盘报告已生成。

## 四、适用性

**适合**：角色可分(CC#1+CC#2+≥1外部) | 标准可量化 | 时间≥4h

**不适合**：单人单AI | 实时调试 | 高度探索性 | 需求剧烈变动 | <200行脚本
