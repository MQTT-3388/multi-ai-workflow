## v1.0 — 初始版本（线性流水线）

### 触发源
C题"五一五日自驾游"项目启动。用户需协调3个AI（Claude Code审查者 + Claude Code执行者 + Gemini建模者）完成问题二。

### 核心架构
```
审查者(CC#1) → 执行者(CC#2) → 建模者(Gemini)
（线性，各干各的）
```

### 模块清单（11个）
| # | 模块 |
|---|------|
| 1 | 角色定义（三角色：审查/执行/建模） |
| 2 | 阶段规划（5阶段） |
| 3 | 审查分级（A/B/C三级） |
| 4 | 阶段阀门（通过/修改≤3轮/驳回） |
| 5 | 同步加固（4触发点+交接快照） |
| 6 | 项目终审（硬约束+静默bug+清单） |
| 7 | 归档标准（6类目录） |
| 8 | 外部代码搜索（竞赛/非竞赛双模式） |
| 9 | 代码生成路由（高难度判定+模型分配） |
| 10 | 多AI交叉审查（双盲独立审查） |
| 11 | 混合模式协议（本地+网页端） |

### 关键能力
- 审查与执行分离
- 阶段阀门质量控制
- 外部代码搜索（web-access→GitHub/论文）
- 双盲交叉审查
- 交接快照防失忆

### 关键局限
- 架构描述不准确（实际是星型中枢，被描述为线性流水线）
- CC#2定位错误（描述为"执行者"，实际价值是"保护上下文"）
- 外部模型被单一化为"建模者"，实际是多功能工具群
- 没有需求讨论环节
- 没有上下文保护机制
- 没有断点恢复能力

### 交付物
- SKILL.md（v1.0）
- 使用教程.txt
- spec.md / usage-guide.md / iteration.md

## v1.0 → v2.0 — 星型中枢重构

### 触发源
1. **C题项目复盘**：CC#2执行者复盘 + CC#1审查者复盘
2. **Gemini Pro第1轮审阅**：指出JSON契约、伪代码预审、模型图谱缺失
3. **Gemini Pro第2轮审阅**：指出判定阈值、防御断言、降级策略缺失
4. **深水区三问**（CC#1发起）：混合模式协议、快照健壮性、审查最早介入点
5. **Gemini Flash终审**：指出控制论框架、上下文屏障价值、人机总线
6. **用户实际用法的系统化**：CC#1中枢 + CC#2副手 + 外部模型群的真实三角色

### 核心变更

| 变更 | 从 | 到 |
|------|----|----|
| 架构 | 线性流水线 | **星型中枢**（CC#1控盘） |
| CC#2定位 | 执行者 | **保护CC#1上下文的副手** |
| 外部模型 | 1个建模者 | **5类按需工具群** |
| 审查层级 | A/B/C | **A/B/C/D**（新增D级跨模型交叉） |
| 交叉审查 | 可选建议 | **模块7硬性规则**（3层降级） |
| 用户角色 | 未定义 | **模块9：只读中继协议** |
| 上下文 | 未涉及 | **模块8：上下文保护**（分流+告警） |

### 新增模块

| # | 模块 | 说明 |
|---|------|------|
| 7 | 强制交叉审查 | 重大结果必须≥2轮独立审查。3层降级（标准/会话/单点） |
| 8 | 上下文保护 | CC#2分流规则 + CC#1告警原则 |
| 9 | 用户中继协议 | 只读中继+无损传递+一键交接+Tab硬隔离 |
| — | 阶段0 | brainstorming需求初探（启动前硬性门禁） |
| — | Skill联动体系 | 深度3+中度5+轻度9=17个skill集成 |

### 被合并的模块
- 原模块8（外部代码搜索）+ 原模块11（混合模式）→ 合并入任务路由和外部模型群章节

### 关键提升
- 架构描述与实际协作方式吻合（94%吻合度）
- 多人验证的审查体系
- 用户操作规范明确
- 外部工具生态集成

### 遗留问题
- 无断点恢复能力（DeepSeek/VSCode无持久记忆）
- 无上下文切换机制（1M tokens不够时怎么办）
- 无阶段回溯能力（阀门通过后无后悔药）
- CC#2无独立的上下文管理

## v2.0 → v2.1 — 基础设施升级

### 触发源
1. **DeepSeek-v4pro无持久记忆**：关闭会话=全部丢失
2. **CC#2在VSCode终端运行**：关闭终端=全部丢失
3. **以天/周为周期的项目需求**：需要跨天恢复
4. **上下文老化风险**：1M tokens被噪声占满→决策质量下降
5. **中途切换模型需求**：API限制或需要更强模型
6. **Gemini对断点恢复方案的评审**：确认方案·补充原子回溯和环境对齐检查
7. **用户提出阶段回溯需求**：阀门通过后发现方向错了能否回退

### 核心变更

| 变更 | 从 | 到 |
|------|----|----|
| 模块5·同步加固 | 4触发点+交接快照 | **完整检查点系统**：`项目状态_当前.md`统一快照 |
| 模块5·关机协议 | 无 | 关机前5分钟写入检查点→第二天新会话30秒恢复 |
| 模块5·上下文切换 | 无 | CC#1安全切换点规则+CC#2自我切换规则 |
| 模块5·阶段回溯 | 无 | 阀门历史快照 `.workflow_history/` + git tag + 原子回溯指令 |
| 模块8·上下文保护 | L1分流+L2告警 | **四层防御体系**（L1→L2→L3→L4） |
| 模块8·CC#2告警 | 无 | CC#2独立告警信号（倾倒日志/反复修改/失忆） |
| 维护责任 | 用户手动 | CC#1自动输出检查点文本（用户只复制粘贴） |

### 四层上下文防御体系（模块8升级）

| 层 | 名称 | 功能 | 触发 |
|----|------|------|------|
| L1 | CC#2分流 | 代码/日志/调试→CC#2，CC#1只看信号 | 任务路由规则自动 |
| L2 | 告警信号 | CC#1(退化/回看/跨阀门) CC#2(倾倒日志/反复修改/失忆) | 信号出现时手动 |
| L3 | 检查点切换 | 写入 `项目状态_当前.md`→新会话→恢复 | 告警触发/阶段阀门 |
| L4 | 磁盘快照 | 关机/崩溃→从文件冷恢复 | 阀门通过自动/关机前手动 |

### 检查点文件 `项目状态_当前.md`

```
统一快照，覆盖全部场景：
- 骨架（项目目标·阶段清单·角色配置）
- 当前状态（阶段·已通过·待裁决·下一步）
- 决策记录（只记结果）
- 数据契约（防失忆核心）
- CC#2恢复用（产出·当前任务·阻塞·关键路径）
- 外部模型状态
```

一个文件 = 冷启动 + 上下文切换 + 关机恢复 + 模型切换 + 阶段回溯。模型无关，任何AI都能读。

### 新增操作协议

| 协议 | 操作 |
|------|------|
| 关机恢复 | CC#1更新检查点→第二天 `"恢复项目。读取 项目状态_当前.md。"` →30秒恢复 |
| CC#1上下文切换 | L2告警→当前决策完成→写检查点→新会话→恢复。禁止在讨论中途切换 |
| CC#2自我切换 | L2告警→存盘→更新检查点→新会话→恢复→汇报。不需等决策 |
| 阶段回溯 | CC#1读 `.workflow_history/StageX.md` + CC#2 `git checkout stage-X-pass` + 环境检查。仅锚定阀门点 |
| 崩溃恢复 | 全部丢失→从 `项目状态_当前.md` 冷恢复。代码从最后一次 git commit |

### 防维护疲劳机制

- CC#1硬性指令：阀门通过后**自动输出**检查点完整文本，用户只负责Ctrl+C/V
- CC#2硬性指令：每次产出后立即保存到磁盘
- CC#2硬性指令：每完成可运行小功能 `git commit -m "wip: [简述]"`

### 关键提升
- 项目规模从"受限于上下文窗口"→"受限于磁盘空间"
- 任何AI组件可随时被替换或重启
- 操作复杂度增加极小（每次阀门通过多一个文件保存操作）
- 完全模型无关：DeepSeek写的检查点，Claude/GPT照样能读
